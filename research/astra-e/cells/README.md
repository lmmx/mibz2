# Packed eager Cells

This research arm uses eager Cells' interval exchange with compact slots and in-register short return words. Its indirect-reference baseline is the eager 20-byte top slot plus the 8-byte bottom slot in `src/cells.rs` at scorer-master commit `9c31461df7bef24cecf79348545b27ee26846835`. The lazy baseline admits up to three capped records per 20 rows, and this candidate keeps its density, sparsity and cell-budget gates. A failed attempt uses the shipped Segmented kernel. All other front-end, RLE1, CRC, worker, and allocator behavior comes from mibz2.

**Reason for this test.** The original eager path admits 196 of the 233 large Wikidata blocks, compared with LazyCells' 228. Comparing to eager alone would therefore also price different fallback rates. On frozen, the 0.5.6 Cells replay charged 0.717 DRAM B/B to its short-word arena, and counted 63,860 short products among 92,570 total cuts. Packing five payload bytes in the descriptor removes both arena addresses from those products, at the price of more grammar rules. These costs and the measured instruction/IPC tradeoff for Open-Return justify measuring the complete new path. ## Construction and mark invariant

1. Count one letter per maximal run and split its interval at the primary row and the following row. Count capped records of the same byte as a single run across their boundaries. An exclusive prefix sum of the 256 letter counts gives each byte's first bottom slot. The second pass writes a pair of slots per letter in stable order. Both passes include the work needed to recognize caps and to validate the tiling.
2. The first word of a top slot packs its top predecessor, row width and opposite slot in three twenty-bit fields. The second word is its return-word descriptor. The bottom slot holds its bottom predecessor and top partner. The two- and one-sided eliminations in the eager induction preserve the shipped order, replacing exhausted front slots as promised by the original construction. All row widths, field indices and lengths are bounded by the input size (at most 900,000 in a bzip2 block).
3. A return-word descriptor contains a twenty-bit length, the mark bit, three spare bits, and forty payload bits. At length at most five, the payload is the actual low-endian byte sequence with zero high padding. Given two inline children of lengths `i,j` with `i+j <= 5`, OR-ing the first payload with the second shifted by `8*i` spells their concatenation. Every longer product appends the two child descriptors to a binary-rule vector and stores its index in that same field. Children always precede parents. This also covers every joining operation containing the marked byte.
4. The marked singleton has width one. Whenever it participates in a cut, the new cell has width one and consumes the entire marked operand. Exactly one live interval therefore carries the mark until it closes. Its initial offset is zero. Joining an unmarked left operand to a marked right operand adds the left word length to that offset. A marked left operand retains its offset. At closure the computed offset is the mark's exact byte index in the root. This permits marked short products to stay inline. The marked path need never be retraced through the grammar.
5. A root of length `n` covers every row. Use the last-use owner certificate of the shipped one-scan writer, scanning rules from newest to oldest, assigning each child a single position and compacting the surviving-child commands into consumed records. All positions are assigned before they are read because the full-period owner tree spans every rule. An unchanged child rule in two adjacent stored rules must have survived in that live operand. If it survives, the immediate next cut also creates a stored rule because the surviving rule already has length greater than five. These are exactly the two directions required for the certificate at this new cutoff. The cyclic root position is `n-1-mark_offset`. An immediate factor containing the cut can wrap, so its literal writer splits at the end of the output. Every deferred copy spans an unmarked contiguous factor, and its descendants have been filled by the time the command executes. Roots shorter than the block use Segmented through the ordinary marked LF contract.

The bottom table borrows aligned space in the output vector. The writer reuses the dead top table for positions. The implementation uses Rust bounds checks for all indexed rows, slots and commands. Its only casts use the standard slice alignment operation on fully initialized integer buffers. Long-rule births use ordinary vector growth. This, room for the bottom table and fallback scratch must all be counted in a peak-memory comparison. The cutoff can increase rule and writer work, and omitting eager's prefetches can increase stalls. These are open cost questions.

## Reproduction

From the repository root, use its pinned Rust toolchain. The property suite compares all chosen marks to a separate stable-sort inverse LF walk. Of 62,286 small marked columns the forced structural route reconstructed 7,237 and declined 55,049. Another full-cycle check accepted all 639 marked rotations across a long cap-split run and all byte values. A two-letter example with very few slots tested the position-space fallback at 3,060 cap-adjacent choices. These tests exercise the research path independently of production's admission line.

```sh
export MOONSHOT_CANDIDATE=research/astra-e/cells/packed.rs
cargo test --manifest-path bench/moonshot/Cargo.toml candidate::checks -- --nocapture
PACKED_CORPUS="$PWD/corpora/wikidata.bz2" PACKED_CSV="$PWD/packed-geometry.csv" \
  cargo test --release --manifest-path bench/moonshot/Cargo.toml \
  candidate::checks::corpus_geometry -- --ignored --nocapture
bash research/astra-e/score.sh packed-round1 "$MOONSHOT_CANDIDATE" --with-opend
```

The corpus geometry test checks each accepted output byte against the shipped multi-lane Segmented reconstruction and logs actual table sizes, rule counts and capacities per large block. The scorer supplies the independent libbzip2 gate and whole-worker comparison. The raw property-suite output is in `property-test.log`.
