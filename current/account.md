A registered workstation test found that using two service threads made decoding 4.5% faster at ten threads while using 12.7% less processor time. The team has not adopted it: the Guardian is holding further service-core timing and production use until targeted safety evidence is reviewed. Separately, two ways to build a decoding table from symbol runs are being developed; one diagnostic is frozen but awaits its own safety evidence before CI timing, while the other is still being revised.

## What has the service-core test established?

The [matched result](https://github.com/lmmx/mibz2/pull/145#issuecomment-6729896575) compared the two-service-thread arrangement with the released 0.2.6 default. Its ten-thread speed ratio was 1.045 (95% interval 1.017–1.073); its processor-time ratio, expressed as default divided by test arm, was 1.146, or [12.7% less processor time](https://github.com/lmmx/mibz2/pull/145#issuecomment-6730014313). Peak memory was 64 MiB versus 74 MiB. The run was valid and favored this arrangement for that comparison, but it did not admit a production change. A separate two-service versus plain two-by-three comparison was faster, while a pipelined two-by-three plan lost to the released default; those comparisons do not isolate a single cause of the ten-thread gain. Trace evidence showed spare service capacity and time waiting for prepared input, which suggests a preparation bottleneck without proving it.

The [Guardian's review](https://github.com/lmmx/mibz2/pull/145#issuecomment-6730103867) found no concrete invalid access, but held further service-core timing and production admission because safety tests had not reached the service decoder path and mutation evidence was insufficient. The [Coordinator accepted the hold](https://github.com/lmmx/mibz2/pull/145#issuecomment-6730114756) and is building targeted evidence. A proposed lookahead change is being checked as an admission threshold, not assumed to be a strict window cap. Once the safety issue is resolved, a further run still needs its own registration and qualification; Louis has no service-core run ready to execute now.

## Why is the released plan being revisited?

Version 0.2.6 was [released](https://github.com/lmmx/mibz2/pull/145#issuecomment-6706739698) after a passing registered confirmation, but later [low-compression-level diagnostics](https://github.com/lmmx/mibz2/pull/145#issuecomment-6720088760) measured its default about 23–24% slower than 0.2.4 on the ten-core workstation. Choosing the older worker plan removes that measured loss in the diagnostic. That change also changes aspects of the plan beyond worker count, so it does not prove one scheduling knob caused the whole difference. Other [boundary](https://github.com/lmmx/mibz2/pull/145#issuecomment-6719903152) and [workload-size](https://github.com/lmmx/mibz2/pull/145#issuecomment-6719949774) tests constrain a replacement policy; none qualifies a new default. The [Researcher also identified evidence and causal limits](https://github.com/lmmx/mibz2/pull/145#issuecomment-6729233463) in the general-plan diagnostics.

Separately, the [Guardian is holding production pipeline safety admission](https://github.com/lmmx/mibz2/pull/145#issuecomment-6729223027) pending reached-path fuzzing and mutation evidence. The Coordinator [accepted that hold](https://github.com/lmmx/mibz2/pull/145#issuecomment-6729235916). It does not erase the historical release measurement; it is a current safety decision about that path.

## What is happening with run-fed tables?

The first [run-fed diagnostic](https://github.com/lmmx/mibz2/pull/145#issuecomment-6729954664) tests whether collecting symbol runs can make the complete decoding-and-table-building stage faster. The Researcher approved its corrected design for freeze, but the [Guardian held CI timing](https://github.com/lmmx/mibz2/pull/145#issuecomment-6729932417) until emitter and fallback safety evidence is complete. The Coordinator is building that evidence; the frozen measured inputs remain unchanged. There is no qualified performance gain from this arm yet.

A second [helper-side design](https://github.com/lmmx/mibz2/pull/145#issuecomment-6730026367) is still under revision. It compares ways to form the table, including direct placement of sorted runs, which the Optimiser now favors as the main candidate. An additional pair-table construction from run intersections is an algebraic option, not a native speed result. Louis's [recorded direction](https://github.com/lmmx/mibz2/blob/cb02fd95/docs/team/PROTOCOL.md#11-run-fed-work) says a negative result on one arm closes that arm, not the whole run-fed search.

The workstation queue has a wait option and a comments-only fix. Neither creates a ready run while these holds and reviews remain. The [supporting levels](L2.md) give the evidence and limits behind this account.
