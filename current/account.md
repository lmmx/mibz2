mibz2 0.3.4 now gives independent blocks to separate processor cores through nine threads, switching to cooperative teams at ten. A valid comparison on Louis's i9 found the independent approach faster at six through nine threads; Louis accepted its extra processor cost at nine and chose the new threshold. The team is examining whether a smaller per-block memory footprint could move that switch further, but the first proposed layout build was withdrawn after its saving was recalculated.

## Why did the threshold move?

The earlier threshold was six physical cores, set before the recent Cells improvements. The Coordinator registered a [direct comparison](https://github.com/lmmx/mibz2/pull/145#issuecomment-6896455773) of the released plan with one block per worker. Its first workstation run [failed its own sanity check](https://github.com/lmmx/mibz2/pull/145#issuecomment-6896638632): the forced-worker arm kept fewer blocks in flight even where it should have run the same plan. That recipe error made the run invalid for the decision.

The corrected run [passed the sanity check](https://github.com/lmmx/mibz2/pull/145#issuecomment-6896798131) and found one block per worker 14%, 11%, 8% and 4% faster in wall time at six, seven, eight and nine threads. Teams were faster at ten. At nine, independent workers used 12.4% more CPU, above the registered 10% flag, so the Coordinator referred that trade-off to Louis rather than taking it automatically. Louis [chose teams from ten](https://github.com/lmmx/mibz2/pull/145#issuecomment-6896854245), while threads sharing physical cores continue to use teams. The change merged in [#425](https://github.com/lmmx/mibz2/pull/425) and shipped as [0.3.4](https://github.com/lmmx/mibz2/pull/145#issuecomment-6897858125). The run is evidence for this i9 and workload; the newly queued 0.3.4 release comparison has no covered result.

## Why look at per-block memory?

Across the corrected run, the independent workers' advantage shrank as their combined table working sets approached the i9's shared cache, and reversed just beyond it. The Coordinator [registered that as a hypothesis](https://github.com/lmmx/mibz2/pull/145#issuecomment-6897826122), not a measured cache-miss cause: memory bandwidth could also explain the pattern. Louis asked MONODROMY to build a layout bringing a block below roughly 1.8 MiB, so ten blocks might fit with room to spare.

MONODROMY's first [size estimate](https://github.com/lmmx/mibz2/pull/145#issuecomment-6897885393) suggested combining a smaller top slot with a narrower rule record. Reading the writer exposed a missing cost: short words would need stored lengths, and packing those lengths into spare offset bits would fail the forced-route size range. Its [correction](https://github.com/lmmx/mibz2/pull/145#issuecomment-6897897097) puts that combination near 1.84 MiB for a median block, with only a few blocks below the target. The already rejected smaller top slot alone reaches about 1.90 MiB and 31 of 196 blocks. MONODROMY therefore has **not started a build**. It suggested testing whether smaller-buffer blocks already cross the threshold differently, but no new test or Coordinator decision on that suggestion is covered here. The cache explanation and a path to another threshold move remain unproven.

## What else is moving?

The 0.3.3 update to [wikidata-pq](https://github.com/lmmx/wikidata-pq/pull/227) remains open. Its first workstation version-ladder attempt took no measurements because a required compression program was missing; the [preflight was repaired](https://github.com/lmmx/wikidata-pq/pull/229), and the ladder is now running through the [downstream queue](https://github.com/lmmx/wikidata-pq/pull/230). A bench observation that decoder work is roughly 4% of this pipeline's CPU helps explain why decoder-only gains have appeared flat end to end; it is not a completed version-ladder verdict.

The [team-threshold release runbook](https://github.com/lmmx/mibz2/pull/426) now calls for retesting a release that changes either side of the switch. Master lists the 0.3.4 threshold and release-scaling workstation jobs, but the Coordinator says their ready tags wait for the downstream ladder summary. Listing a job is not evidence it has run.

The [post on eight-byte bottom slots](https://github.com/lmmx/mibz2/pull/427), titled “Removing duplicated interval lengths and text references,” has been published after a fresh-reader pass and Louis's editorial choice. Separate workstation tooling now announces starts and failures and stores logs under XDG state, and wikidata-pq has the same queue. These changes support future runs; they are not decoder-speed findings.

## What remains uncertain?

The first threshold run stays invalid despite its suggestive figures. The corrected result supports the released switch on one machine, while its memory cost at nine threads is an owner-accepted trade-off, not a passed 10% rule. Cache capacity is a plausible explanation for the crossover, but no cache-miss or block-size intervention has established it. The narrower-rule estimate was corrected before a build, so no candidate or benchmark exists for it.
