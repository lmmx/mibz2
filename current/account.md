## Why did the fallback explanation change?

An [earlier investigation](https://github.com/lmmx/mibz2/pull/145#issuecomment-6734039197) showed that the old all-fallback penalty could not readily be explained by record construction: the arms called the same hot kernels and did almost the same counted work. It also found different stack-address geometry. The [Optimiser’s review](https://github.com/lmmx/mibz2/pull/145#issuecomment-6734171410) showed that this does **not** establish stack layout as the cause. A one-kilobyte address-dependency pattern could affect all arms, while process memory placement remains another possibility. The [corrected journal](https://github.com/lmmx/mibz2/blob/fa180e14f2cec85bb1a2a13cde8ac777fd9957cc/docs/journal/2026-11-09-run-fed-fallback-codegen.md#6-correction-what-the-evidence-supports) calls for a crossed layout and process control; it has not run. No adjusted speed credit or CPU-family explanation follows. The registered run-fed verdicts remain as measured.

## What else is being tested?

The register-based decoder supplied much of the earlier run-fed CI gain. As a separate production prototype, it has [safety clearance for a bounded diagnostic](https://github.com/lmmx/mibz2/pull/145#issuecomment-6733356125), but its registration is still a draft. The Researcher found that a run without the intended AVX2 path or sufficient CPU capacity could be judged; the first repair closed those cases. A [later review](https://github.com/lmmx/mibz2/pull/145#issuecomment-6734701311) found that an unknown CPU quota still looks like a known unlimited quota to the reporter, allowing another false judged result. That encoding is being repaired. There is no qualified production speed gain.
