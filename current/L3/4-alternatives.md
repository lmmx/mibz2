# 4. Alternative decoder architecture

## Service-core

- **Purpose:** test whether dedicated service threads improve whole-decoder wall and processor cost, in order to serve 0 ([registration](https://github.com/lmmx/mibz2/pull/258)).
- **Established:** #258's valid ten-thread comparison returned speed 1.045 (1.017–1.073), 12.7% less CPU, RSS 64 versus 74 MiB; FOR SVC2@10, not adoption ([result](https://github.com/lmmx/mibz2/pull/145#issuecomment-6729896575), [correction](https://github.com/lmmx/mibz2/pull/145#issuecomment-6730014313)).
- **Premise:** preparation starvation was observed, but a larger lookahead admission threshold has not been proved to improve wall time. Prepared occupancy can reach L+K−1; it is not a strict L cap. Service idle does not itself prove an eligible preparation opportunity ([Researcher](https://github.com/lmmx/mibz2/pull/145#issuecomment-6730484783)).
- **Status:** Guardian D057 lifted D045/D053 for the named runtime scope; Researcher [PROCEED](https://github.com/lmmx/mibz2/pull/145#issuecomment-6732841051) closed #271's false-VALID evidence objection at runnable head 8a0fc8e099f932c14cd746c4c5d81aaef8dcc75d. The ready tag belongs on that head, not its measured-input ancestor. Coordinator's [run-signal dispatch was refused](https://github.com/lmmx/mibz2/pull/145#issuecomment-6732854512), so the tag and queue line await Louis; no new speed result.

## Run-fed table construction

- **Purpose:** test whether run records can reduce complete move-to-front and table-building cost, in order to serve 0; an arm's STOP pauses that arm on its runner, not the line ([PROTOCOL §11](https://github.com/lmmx/mibz2/blob/cb02fd95/docs/team/PROTOCOL.md)).
- **#269 serial arm:** D048 closed D044 for the one frozen CI diagnostic. Run 42549324025 was VALID, Q1 STOP on its pinned worker: R_stage 1.1592 (1.1387–1.1801). The fill beat today's build, but emitter, sort and fallback costs outweighed it. The fallback phase excludes selection; nominal phase medians are not an exact counterfactual ([result](https://github.com/lmmx/mibz2/pull/145#issuecomment-6730764444), [Optimiser](https://github.com/lmmx/mibz2/pull/145#issuecomment-6730842547)).
- **#272 pair path:** its valid registered Q1 builder/row-builder ratio 0.6865 remained INCONCLUSIVE against ≤0.50, and Q2 whole pair/production 1.8950 was NEGATIVE STOP. Optimiser replay and Researcher review did not change the verdict. The [corrected journal](https://github.com/lmmx/mibz2/blob/6b36fd8c/docs/journal/2026-11-09-pair-from-runs-result.md) withdraws the claim that residuals are walk-only intervals or that no builder can carry Q2: they subtract separate sweeps with different setup/admission. Against production's one-hop builder, the run-pair builder loses on every measured paired corpus ([Optimiser](https://github.com/lmmx/mibz2/pull/145#issuecomment-6731728422), [Researcher](https://github.com/lmmx/mibz2/pull/145#issuecomment-6731804749)).
- **Consumer premise:** paired arithmetic gives a roughly 2.088 nominal c/output-byte residual difference against production, but that residual includes setup/admission and is not a consumer-only interval. A prospective pre-built consumer test is needed. Researcher derived certified output packets using at most 3r−2 refined cells, an untimed construction option ([review](https://github.com/lmmx/mibz2/pull/145#issuecomment-6731804749)).
- **#270 helper-side arm:** its registered nine-thread CI attributed LEAD stands. Workstation §8 timing registration is specified for seven arms, twenty paired rounds and requested ten threads, but Researcher [REVISE](https://github.com/lmmx/mibz2/pull/145#issuecomment-6733680620) found five occupancy captures incorrectly accepted as interpretable. Guardian D061 [found census-hook scope/cost claims to correct](https://github.com/lmmx/mibz2/pull/145#issuecomment-6733631922); D062 [retains REVISE](https://github.com/lmmx/mibz2/pull/145#issuecomment-6733983929) on the assertion that the feeder always joins before capture take. No new B5 HOLD, workstation freeze or run. Paired dir/reg remains descriptive rather than isolated direct-fill causality.

- **#277 direct one-hop arm:** its valid Q1 STOP at D/A 1.0525 remains. Optimiser [replay](https://github.com/lmmx/mibz2/pull/145#issuecomment-6733249734) and Researcher [review](https://github.com/lmmx/mibz2/pull/145#issuecomment-6733290162) reject a simple “equal slots therefore scattered writes” attribution: predicted store operations, dependencies, tails and access pattern differ. The measured placement/(sort+fill) 1.2045 is a compound contrast. On all-fallback corpora, B/A's large penalty occurs without record construction. [#283's static investigation](https://github.com/lmmx/mibz2/pull/145#issuecomment-6734039197) traces it to harness stack layout, with 4 KiB aliasing a plausible but untested hardware mechanism. Neither #277 nor #269's registered verdict reopens.
- **Runner contrast and line:** sorted B/A was 0.9763 in #277's AMD run and 1.1592 in #269's Intel run. Baseline and harness context also changed, so CPU-family causality is not identified. A proposed common-fallback, crossed-layout control has not run ([journal](https://github.com/lmmx/mibz2/blob/adb16fb75cb7e25eb734aeebf4cc9e7bf28ff8c5/docs/journal/2026-11-09-run-fed-fallback-codegen.md)). The self-repeating packet census paused its narrow arm; later Researcher review [qualified its coverage](https://github.com/lmmx/mibz2/pull/145#issuecomment-6733146738) without reviving a timing claim. §11 keeps the line open.
