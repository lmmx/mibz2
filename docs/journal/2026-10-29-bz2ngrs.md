# bz2ngrs: a second segmented inverse BWT, read and measured beside ours

[bz2ngrs](https://github.com/Softleif/bz2ngrs) (Softleif, Apache-2.0 WITH LLVM-exception) is
a bzip2 decoder and encoder in safe Rust, ported from bz2-ng's C
([tfenne/bz2-ng](https://github.com/tfenne/bz2-ng)). Its README claims bz2-ng's speed,
"about even on x86-64", and one thread a stream. Its inverse BWT uses the same structure
as ours: a 32-bit T-vector, segments walked as interleaved lanes, then joined. That makes
it a direct comparison for mibz2's kernel on one core. This entry records what its source
does, how the two were measured against each other, and what the comparison opens.

Labels as in the other entries: **source** (read at the commit given), **measured** (a run,
said where), **hypothesis** (untested).

## 1. What its inverse BWT does (source: `src/bwt.rs` at 6a92590)

| | bz2ngrs | mibz2 (`src/bwt.rs`) |
|---|---|---|
| entry | `(i << 8) \| F[j]` at row j, i its L position: the row's **first-column** byte | `(i << 8) \| L[j]` at row j (lbzip2's packing): the row's **last-column** byte |
| build | an 8-part count of L (independent counters, for L's runs), prefix sums, then the scatter in two passes of 4 parts: **write-only** stores | counts from MTF; an **init pass** writing L's bytes into the table, then the scatter as a **read-modify-write** of each entry's high bits, with 16-row run stores (libsais's RUN_LANES, #32) |
| segment starts | evenly spaced rows, n / 512 of them, at most 510 (about 1,765 rows each at 900 k), plus `orig_ptr`; marked in the entry's top bit | pseudo-random rows, marked in the entry's top bit |
| walk | 24 lanes in lock step (8 below 4 Ki rows); no software prefetch | 32 lanes, the room walk; a prefetch to L1 each step |
| output | 1 KiB chunks in **L's own buffer**, free once the build has read it, linked chunk to chunk | a buffer per segment (`SegScratch::bufs`) |
| join | `gather`: the chunks copied into the block in text order | `SegScratch::assemble`: the segments copied into the block |
| arrays | fixed: 4 MiB table (2²⁰ rows), 1 MiB L, 1 MiB text | sized to the block |

- **Its module doc is stale.** It says "a table build in four interleaved quarters", but
  the code has `PARTS = 8`, scattered four at a time ("eight at once spill on x86-64").
  An outside summary repeated the doc's "four quarters".
- **The two walks emit the same text, one position apart.** The link is the same in both
  layouts (row j's high bits hold the i with LF(i) = j). bz2ngrs emits F[j], our walk
  L[j], and both move forward through the text. So the byte beside the link is a free
  choice.
- **Why bz2ngrs can make its scatter write-only:** at scatter time the byte it stores is
  `L[i]`, already in hand, and that is F[j]. Our packing stores L[j], a different row's
  byte. That needs the init pass first and a read before each store.

## 2. How it is measured (all in bench/alternatives, never published)

- **The whole decoders:** examples/ab.rs, as for every alternative, on one pinned CPU,
  each output hashed and compared:
  - `bz2ngrs` (its `DecompressReader`) and `bz2ng` (bz2-ng's C `bzip2 -dc` through a
    pipe);
  - with libbzip2 and libbz2-rs as before;
  - `mibz2-oneshot` and `bz2ngrs-oneshot` (the file read whole, decoded into one Vec):
    each pair of streaming and one-shot runs shows a reader's own cost.
- **The inverse BWT alone:** `kernels` (bench/alternatives/src/kernels.rs).
  - bz2ngrs's `src/bwt.rs` is copied as it is, with its notice. Only a timed copy of
    `inverse` is added, and `zeroed_box!` is defined locally. A check confirms the copy's
    body is byte-identical to the original's.
  - Both kernels run on the same blocks' last columns, in decode order, the kernels'
    order alternating by pass.
  - **Correctness, untimed:** before timing, every block's bytes must be the same from
    both kernels, and must RLE1-decode to the block's CRC.
  - **The boundary between phases:** mibz2's build takes its counts from MTF, while
    bz2ngrs's counts L itself. So `count_only` (bz2ngrs's own counting loop) is timed
    apart, and the builds can be compared either way.
- **`just bench-compete`** (bench/compete.sh) runs both on a quiet machine, then perf's
  hottest symbols (user cycles) for mibz2, bz2ngrs and bz2-ng's C where perf works. It
  writes compete-<time>.md with the raw `.jsonl` and `.kernels.jsonl`.
- **On CI:** bz2ngrs and bz2ng are now arms of master's benchmark (bench 3.1.0). The
  kernels' table sits beside the stage table, so both appear on the site's Alternatives
  page.

**The whole decoders, one core** (2 rounds, wall time over mibz2's paired by round; every
output the same bytes):

|---|--:|--:|--:|
| mibz2 | 1.45 | 1 | 27 MB |
| bz2ngrs | 1.69 | 1.17 | 12 MB |
| mibz2-oneshot | 1.45 | 1.00 | 228 MB |
| bz2ngrs-oneshot | 1.67 | 1.16 | 220 MB |
| bz2ng (C) | 1.38 | 0.95 | 6 MB |
| libbzip2 | 6.63 | 4.58 | 8 MB |
| libbz2-rs | 6.47 | 4.42 | 8 MB |

A second 2-round run gave bz2ngrs at 1.30 × mibz2 and bz2ng at 1.11 ×. With 2 rounds, the
intervals span both readings.

**The inverse BWT alone** (6 passes, median ns per byte of last column):

| phase | mibz2 | bz2ngrs | bz2ngrs / mibz2 (95%) |
|---|--:|--:|--:|
| build | 0.888 | 1.462 | 1.67 (1.59–1.75) |
| walk | 3.049 | 3.494 | 1.14 (1.06–1.23) |
| assembly / gather | 0.200 | 0.174 | 0.86 (0.78–0.94) |
| total | 4.138 | 5.123 | 1.24 (1.16–1.33) |

bz2ngrs's count alone is 0.37–0.44 ns/B, of its 1.46–1.55.

**Read with the VM's caveats:** its L3 is 33 MB, so nothing is under capacity pressure.
The workstation run decides.
- **Where the gap is:** at 1.24× the inverse BWT accounts for about half the whole
  decoder's gap on this run. The rest is in its other stages or its reader; the one-shot
  pair puts the readers at about even.
- **Build:** bz2ngrs's is 1.5–1.7× slower, its count included. Net of the count, its
  scatter (about 1.0–1.1 ns/B) is about even with our whole build, init pass included.
  **So the write-only scatter is not shown faster here.** Our 16-row run stores carry
  Wikidata's long runs; bz2ngrs has no run path.
- **Walk:** ours is 12–14% faster. Its lanes are fewer (24 against 32) and it has no
  prefetch. Which of those matters is not measured.
- **Gather:** bz2ngrs's is 10–15% faster, but that is 0.026 ns/B, under 1% of the
  inverse BWT.
- **bz2ngrs's C original is faster than the port on this x86 machine** (0.95–1.11 × mibz2
  against 1.17–1.30 ×). That is consistent with its README's "about even on x86-64" being
  approximate.

- **The gap is Wikidata's, and it is the inverse BWT.**
  - bz2ngrs is even with mibz2 on text, records, runs, random and onebyte, but 1.45×

    difference;** the rest of the decoder is even.
- **The build:**
  - Net of its count, bz2ngrs's scatter is about 0.96 ns/B against our whole build's
    0.69, so ours is about 1.4× faster.

    doesn't make up for having no run path.**
- **The walk:** on the EPYC, bz2ngrs's is 1.72× slower (1.14× on the VM).
  - The difference between the two machines is consistent with our prefetch and 32 lanes
    mattering more on this core. That is a hypothesis: neither is measured apart.
  - So the walk is the larger gap here (1.09 ns/B, against 0.63 for the build).
- **bz2ngrs is faster than its C original on this runner** (1.45× against 1.71×, the C's
  wall equal to its CPU on Wikidata). On the VM it was the other way round. The README's
  "about even on x86-64" holds only loosely.
- **Memory:** bz2ngrs's peak RSS is 0.45 × mibz2's at 1 thread on Wikidata (12 MB
  against 26). bz2ngrs's reader holds about 6 MiB of working memory, 1 MiB of input and
  one block's output (its docs). mibz2's 26 MB isn't broken down here.

**What this changes in §4:**
- **Hypothesis 1 (first-column packing) loses its premise on both machines.** bz2ngrs's
  build is slower than ours even net of its count. A write-only scatter could still help
  *our* run-store build, but nothing here suggests it beats ours.
  - It stays a cheap `kernels` experiment, behind the workstation run.
  - It runs only if the workstation's build row says otherwise.
- **Hypotheses 2 and 3 are unchanged.**

## 4. What it opens (hypotheses, each a bounded experiment, none started)

1. **First-column packing in our build (the write-only scatter).**
   - **The change:** store F[j] beside the link, as bz2ngrs does. That removes the init
     pass over the 3.6 MB table, and the read in each store. The run store becomes a pure
     16-wide store of one constant byte.
   - **What it costs:** the walk then emits F[j] rather than L[j]. Each segment's first
     and last byte move by one, as do the segment marks' and the start's handling. The
     room walk is touched, so it comes with the segment oracle and Miri.
   - **Why it might not pay:**
     - a store to a line not in cache still reads it for ownership (RFO), so the memory
       traffic saved can be less than the loads removed;
     - the init pass's sequential write also warms the table for the scatter.
   - **The test:** our build with first-column packing and run stores, against today's,
     in `kernels` (the build alone, counts on both sides of the boundary).
   - **What weighs it:** on the workstation, 3x3 spends 42% of its time in the build
     (`2026-10-28-cooperative-inversion.md` §7.3). Any build gain counts there for more
     than at p4, so it is re-measured in the coop grid if it wins in `kernels`.
2. **The output in L's own buffer.**
   - **The change:** bz2ngrs writes the walk's output into L's buffer, free once the build
     has read it. Our segment buffers are a further ~0.9 MB a live block (about n bytes).
   - **What it saves, and what it doesn't** (corrected after an outside review): it saves
     an allocation, about 0.9 MB a block of resident memory. It does **not** shrink the
     walk's hot working set.
     - The walk still writes about n bytes of output, into L's lines instead of the
       segment buffers'.
     - L is already dead after the build, so its lines are evictable.
     - So the actively touched bytes in the T-vector phase are about the same either way:
       the 3.6 MB table read, plus about 0.9 MB written.
   - **What could still differ (hypotheses, untested):**
     - the output's stores landing on lines the build has just read (L's), so fewer
       write-allocate misses;
     - less residual occupancy from the segment buffers between blocks;
     - page reuse.
   - **Its effect on the cache knee is unknown.** It is a memory-reuse change first.
   - **The test, if it is ever run:** the room walk writing into L's buffer, with the
     occupancy curve at 6–10 workers on the workstation, and DRAM write bytes per output
     byte from the counters. It stays behind the cooperative work.
3. **Lanes and prefetch.** 24 lanes without prefetch against our 32 with: our walk sweeps
   (`2026-10-27-walk-sweep.md`) already chose 32 and L1, on CI. Nothing to do unless the
   workstation's walk ratio says otherwise.

## 5. Not done

- **Multicore.** bz2ngrs decodes one stream on one thread. A fair multicore comparison
  is N independent streams, each decoded by one process, pinned to its own core, against
  mibz2's block-parallel decode of the same bytes, clearly labelled as such. It is not
  built.
- **perf on the VM:** its perf doesn't match its kernel. bench/compete.sh samples on the
  workstation.

## 7. The faster reference is libsais, not bz2ngrs (2026-10-29)

bz2ngrs has answered its question: on both machines its inverse BWT is slower than ours,
in every phase but the gather. The one inverse BWT measured faster than ours, on the i9
(not on CI's runner: below), is libsais 2.12.1's:
- 1.13 × production's on one i9 core (the cooperative pilot's block mode);
- 1.08 × at 4 independent workers (s4x1);
- 1.20 × our 3x3 at 3x3 (s3x3), in `2026-10-28-cooperative-inversion.md` §7.5.

So libsais joins the kernels' table (bench 3.2.0) as the permanent reference for the
inverse BWT on one core:
- single-threaded, built from the same pinned and checked source as the pilot's;
- its total only, since its build and walk are one call;
- in that table only: it is a library of BWT algorithms, not a bzip2 decoder, so it
  never appears beside the decoders.

**The VM, indicative (6 passes):** libsais 5.62 against mibz2's 5.32 ns/B, 0.99×
(0.82–1.20). This was in a noisy hour, with every kernel about 30% slower than this
morning.

**CI's runner** (an AMD EPYC, the dispatched run of the 3.2.0 branch, 10 passes, every
block the same bytes from all three):

| | mibz2 | bz2ngrs | libsais |
|---|--:|--:|--:|
| inverse BWT, ns/B | 2.339 | 4.039 | 3.370 |
| over mibz2's | 1 | 1.72× (1.70–1.75) | **1.44× (1.43–1.46)** |

**libsais's advantage depends on the machine.**
- On the i9 its single-core kernel is 1.13 × faster than ours.
- On CI's EPYC it is 1.44 × slower.
- On the VM it is even.
- "The faster reference" holds on the i9 only, so far.

**It fits our own record.** Our port of the same two-symbol (ψ²) walk lost on CI's
runners (`2026-10-27-pair-walk.md`), while libsais's wins on the i9.
- **Hypothesis:** halving the dependent loads a byte pays where each load is
  expensive, as on the i9 at its 4 workers and up. It costs where loads are cheap
  enough that the extra work per step dominates.
- **The test:** the i9's `s4x1` against `p4` at 1, 4 and 10 workers (the scaling sweep),
  beside this table on CI.
- If it holds, the two-symbol walk is a per-machine choice. It isn't a kernel to adopt
  everywhere.

The multicore study, the libsais phases (perf) and the ordering against the cooperative
confirmations are in `2026-10-28-cooperative-inversion.md`, once those confirmations are
in.
