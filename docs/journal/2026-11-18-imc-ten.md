# Ten workers against seven at the memory controller (registration)

*Registered 18 November 2026, before any data. The recipe is `just bench-imc-ten` (`.just/bench.just`, `bench/imc_ten.py`). This is a diagnostic. It scores one prediction, adopts nothing, and changes no production default.*

## The prediction, frozen

MONODROMY froze it as record 52, in REVIEW 6973478826 on #145 (point 4), before any of this run's data. Verbatim:

> 4. **Frozen now, for one run:** lazy 10/40 unpinned against 7/28, with IMC and offcore latency. Predicted: DRAM 30.7 [29.0, 32.5] GB/s (at least 88%), and L3-miss latency +20% or more against 7.
>    - *Refuted if:* DRAM is under 80%, or the latency rises under 10%.

The question behind it (the same REVIEW, point 3): past 8 workers, is queueing at the memory controller what makes lazy 10/40 slower than 7/28 unpinned at 10 threads (0.873 [0.866, 0.880], `bench-unpinned`)?

## What runs

**The arms:** `ab child mibz2-occ-10-40 10 FILE` and `ab child mibz2-occ-7-28 10 FILE`. Each is production's decoder with N lazy workers and S blocks in flight, whatever the threads asked: `BzReader::parallel_workers(.., N, S, Kernels::detect(), true)`. These are bench/unpinned's and bench/eager-trim's lazy occupancy arms, ported to this branch alone (`occ_arm` and its arm in examples/ab.rs). The two arms differ in the worker count and the window alone.

**Unpinned, on all 20 CPUs:** each child is started under `taskset -c` with the whole online list (`/sys/devices/system/cpu/online`), as `ab run --unpinned` sets it. A shell between `taskset` and `ab` reads back the affinity it execs `ab` with (`Cpus_allowed_list` in its own `/proc/PID/status`; the shell becomes `ab`). That list is recorded in every run. `ab run --unpinned` itself is not ported: this driver spawns the child and wraps it in perf, so it sets the affinity itself.

**The files:** Wikidata ×4 (judged) and ×1 (a check, reported, not judged).

**The order:** 10 paired rounds. Each round runs both arms on each file, the arms' order alternating by round and by file (ABBA).

**Each run is wrapped**, as bench-knee wraps it (`knee.py`'s `wrap`), from the inside out:
1. `taskset -c` with every online CPU;
2. `perf stat` of the process's own events: `cycles`, `offcore_requests.l3_miss_demand_data_rd` and `offcore_requests_outstanding.l3_miss_demand_data_rd`;
3. `perf stat -a` of the memory controller: `uncore_imc/data_reads/` and `uncore_imc/data_writes/`.

**The idle traffic:** the memory controller's bytes over `sleep 2`, 5 times before the runs and 5 times after (`knee.py idle`). Each event's median idle rate is taken off each run in proportion to its elapsed time, as bench-knee does.

**The ceiling:** re-measured on the same machine in the same units, as bench-knee measures it (`knee.py stream`, `knee.py`'s `ceiling`). `ab stream` runs scale and triad, 256 MiB an array, at 1, 2, 4, 10 and 20 threads, at 2 and 12 repetitions in alternating order, 3 times. The rate is the difference of the two runs' memory-controller bytes over the difference of their kernel times, the idle traffic taken off. The ceiling is the best median over thread counts and kernels.

## The latency counter

The L3-miss demand-read latency, in core cycles, by Little's law: `offcore_requests_outstanding.l3_miss_demand_data_rd` over `offcore_requests.l3_miss_demand_data_rd`. This is bench-miss-cost's counted pair (bench/counters.py on bench/miss-cost, group 5, "L3-miss demand-read latency, cycles").

It was chosen over bench-miss-cost's other latency, `perf record` of `mem-loads` (bench/memlat.py), for three reasons:
- it counts per process, so it needs `kernel.perf_event_paranoid` 1 or less and no root;
- it is read in the very run that the memory controller is read in, so wall, DRAM and latency come from the same runs;
- it costs nothing measurable, where sampling loads would perturb the wall it is paired with.

If perf list doesn't name both events, or their trial fails, the latency is UNMEASURED (the report says so); the run is not VOID for that.

## Measured and reported, per arm and file

- the wall (median), and 7/28's over 10/40's paired by round;
- DRAM GB/s: the median of the runs' idle-subtracted read-plus-write bytes over the median wall (bench-knee's table's figure, which record 52's numbers came from);
- its share of the ceiling;
- DRAM bytes per output byte, reads and writes apart and together;
- the L3-miss latency (the median over runs), and 10/40's rise against 7/28 (the medians' ratio, and paired by round).

## The rule

The verdict reads Wikidata ×4: 10/40's DRAM share of the ceiling (`frac`) and the latency's rise against 7/28 (`rise`, medians):
- **REFUTED** if `frac` < 0.80, or `rise` < 0.10;
- otherwise **SUPPORTED** if `frac` ≥ 0.88 and `rise` ≥ 0.20;
- otherwise **INCONCLUSIVE**. That includes a latency UNMEASURED with `frac` at 0.80 or more.

The report also says whether 10/40's DRAM GB/s falls inside the predicted [29.0, 32.5]. That is context; the rule above is the verdict. The ×1 check is read by the same rule, and reported, not judged.

**VOID**, with no reading:
- the memory controller unreadable. With `kernel.perf_event_paranoid` above 0, no perf, no `uncore_imc` events in perf list, or a failed trial, the recipe says so and stops before building anything;
- any run failed;
- any run's affinity not all 20 CPUs (exactly the online list, 20 of them);
- the arms' outputs differ on a file;
- a cell with no run, or no ceiling in the memory controller's bytes.

## Cost

`bench/imc_ten.py estimate`: 40 decodes (about 17 s), the ceiling (about 48 s), the idle readings (about 21 s), the build (about 150 s) and the corpus (about 30 s). That is about **4.4 minutes of i9 time**, under the 8-minute budget.

## The VM dry run

On the 4-CPU VM (no perf, `kernel.perf_event_paranoid` 2), `just bench-imc-ten 1 1 1 4 1` stopped at once: "VOID, the memory controller is unreadable: perf is not installed; nothing run".

The driver was also run for real there without perf: `ab` built by rustc 1.99.1, both arms, 2 rounds, a 4 MB synthetic file ×1 and ×4. Every run read back its affinity (CPUs 0–3), and the arms' outputs agreed. On the ×4 file's 20 blocks, 9 of 10/40's workers and all 7 of 7/28's showed CPU time (`thread_cpu`). The report was VOID on two counts: the memory controller unreadable, and 8 runs not on all 20 CPUs. Both were expected.

bench/test_imc_ten.py drives the whole path with a stub perf and ab, and covers:
- each threshold on both sides;
- the arithmetic;
- every VOID case.
