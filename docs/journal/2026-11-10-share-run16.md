## 1. The change

`share`'s equal-window body, 16 scalar stores, becomes one call:
`bwt::run16(ll + s, i << 8, slots + s)`. `run16` is made `pub(crate)` and is otherwise
untouched. The classifier (two `read_u64` and the rotate), the guard `s + 16 > lim[c]`, the
one-row step, the tail and the end check are unchanged.

**Safety argument** (in the code, at the call):
- **The guard bounds the window:** `s + 16 ≤ lim[c]`, checked just above.
- **The window is inside the block:** `lim[c] = starts[c] + after[c] ≤ starts[c] + counts[c]
  ≤ n`. `new` checked every checkpoint to be within the counts, the counts to sum to n, and
  `after` is the counts themselves at n.
- **So both ranges are valid:** `ll[s..s + 16]` is readable, and the slots `s..s + 16` are in
  the table's reserved capacity.
- **No other share writes there:** the slots are inside this range's window of bucket c.
  The windows are disjoint because the checkpoints rise (`check_inputs`), the same argument
  as the one-row step's.
- **The entries are exact:** `i + 15 < n < 2^24`, so `(i + jj) << 8` fits a u32 and shares no
  bit with the byte. `run16`'s add is then the OR the scalar code did.
- **All 16 entries are final:** unlike `build_one_pass`'s partial runs, no provisional entry
  is left above the cursor.
- **Proof scope:** the argument covers inputs that `new` accepts. It rests on `check_inputs`
  and the guard, not on the checkpoints being the block's own. Wrong checkpoints are refused
  by the guard or by the end check, and never write outside the window. The refusal tests
  and the guard test below exercise this.

## 2. Tests (before the count)

**The new tests**, all in `src/coop.rs`:

| test | what |
|---|---|

| `share_run16_is_the_scalar_share_on_real_blocks` | the same, on libbzip2's last columns of this crate's sources and a runs corpus, levels 1 and 9, k ∈ {2, 3}, the decoder's stride and 1000 |

| `miri_share_run16_window_guard` | the guard at its edge: a last bucket one slot short, its window ending at n, the table's reserved end. It must refuse and not write; an off-by-one guard writes past the reservation |

**The crafted columns in the first test,** at k = 1 to 4 and strides 1, 3, 7, 16 and 64 (the
ranges' edges at every alignment mod 16):
- one byte throughout;
- alternating bytes, and `aab`;
- a run of 15, 16, 17, 31, 32, 33 or 48 at every offset 0 to 15, followed by tails of 0, 1,
  5, 16 or 17 bytes;
- block ends: an equal run of 16 + r at the end, for every r from 0 to 15;
- two buckets' runs side by side;
- short blocks of 0 to 40 bytes;
- the existing `columns`.

**Results:** the release-mode run of the build's tests (`share_run16`, `build_fused`,
`split`) passed 8 of 8. Miri (nightly, `cargo miri test --lib -- miri_share_run16`) passed
2 of 2 in 94 s. `cargo fmt --check` and `cargo clippy --all-targets --all-features -D warnings`
are clean.

**Mutants of the new window logic,** each run against the release tests:

| mutant | caught by |
|---|---|
| M1: base `(i + 1) << 8` | the native tests, 6 failing |
| M2: source `ll + i`, not `ll + s` | the native tests, 6 failing |
| M3: base `i`, unshifted | the native tests, 6 failing |
| M4: cursor step 15, not 16 | the native tests (`build_fused_is_build`, `miri_share_run16`, …) |
| M5: guard `s + 17 > lim` (stricter) | the native tests |
| M6: guard `s + 15 > lim` (laxer) | **not by the native tests.** Killed under Miri by `miri_share_run16_window_guard`, which reports an out-of-bounds read of `ll`. The test was written after M6 survived (§5) |

**M6 survives natively by construction.** On inputs that `new` accepts with the block's own
checkpoints, the guard never fires. On wrong inputs the off-by-one only adds a stray write,
and the end check refuses the build anyway. The guard exists for memory safety, so a memory
checker is what detects its mutant.

## 5. Deviations, disclosed

1. **Condition 3's registered test cannot discriminate.** It asked for executions of
   instructions in `share` whose debug line is in `bwt.rs`'s `run16`.
   - **What the line tables show:** with `line-tables-only`, the inlined intrinsics' code
     takes its innermost frame's file. The load is `core::arch` `mod.rs:573`, the four
     stores `mod.rs:1963`, the unpacks `macros.rs:173`, the adds `sse2.rs:111`.
   - **So the literal test reads zero in both arms.** It cannot tell them apart.
   - **Read instead by instruction identity:** objdump of `share`'s executed addresses, in
     `share-window-instructions.txt`.
   - **The disposition** of this condition is the Guardian's.
2. **The old binary is not #330's file.** Its SHA-256 is `76f7cf34…`, not `f4f035a5…`, being
   built from another path. Its `src/` is identical (no `src/` change since `ae44497e9`).
   Condition 4 reproduces #330's figures.
3. **No inlining change.** `run16` is `#[inline(always)]` and inlined into `share` as into
   `build_one_pass`. `share` remains one symbol in both binaries, with the same 0.001 Ir/D of
   arcs out.
4. **`miri_share_run16_window_guard` was added after the first mutant run,** when M6 survived
   the native tests. The kernel did not change. The count's binary is from the commit that
   contains the test.
5. **CI's Miri job grows.** The new `miri_*` tests add about 90 s to `cargo miri test --lib --
   miri_` (`.github/workflows/miri.yml`).

### What was wrong: every profile loaded twice for two derived files

- **The order of events:**
  - The three arms were profiled into the scratch directory `run16-count/cg/`, as raw files.
  - `report-old.txt` and `report-new.txt` were made from them, and so were the figures first
    quoted in §3 and §4.
  - To size the archive, I then ran `gzip -k` there. It kept each raw file and wrote its
    `.gz` beside it.
  - The archive step then re-ran `share_count.py` and `share_lines.py` on that directory, to
    write `share-count.txt` and `share-window-instructions.txt`.
- **Why the files were doubled:** the parser's `load(prefix)` takes every file matching
  `PREFIX.PID-NN` or `PREFIX.PID-NN.gz`. So it read 24 files an arm: each thread's raw
  profile and its gzip.
- **Reproduced:** a directory with the archived `.gz` files and their `gunzip -k` copies side
  by side. `load()` matches 24 files, and `share_count.py` prints exactly the archived
  doubled figures: old self 3,748,029,150 (17.873 Ir/D), inclusive 17.875; new self
  2,845,867,142, inclusive 13.573.
- **Why the call count did not show it:** `share_count.py` stored calls per thread in a
  dict keyed by thread number. The second copy overwrote the first, so it still printed 466,
  while the Ir sums doubled.
- **A second defect in `share_count.py`'s line section:** its "max exec" column was a
  maximum over threads, not a sum. It is not an execution count of the whole decode.
  `share_lines.py` sums over threads, as `reconcile.py.txt` does.
- **Not affected:**
  - `report-old.txt` and `report-new.txt`, whose totals equal the once-loaded sums below
    exactly;
  - the profiles themselves;
  - the figures first quoted.

**Superseded files, kept as evidence of the error:**
- `share-count.txt` (sha256 `9ed5a462…`);
- `share-window-instructions.txt` (`e1b457f9…`): its executions are doubled, but its
  addresses and disassembly column are the binary's.

## 9. The independent B5 reviewer's tests, adopted

The independent B5 review of #335 (comment 6759991701) found no material objection. It found
that the native suite was blind to a laxer or missing guard, which only CI's Miri caught. It
supplied three native tests, now in `src/coop.rs`. **They are the reviewer's tests, not the
implementer's.**

| test | what |
|---|---|
| `b5_guard_top_bucket_sentinel` | lying counts that `new` accepts leave the top bucket (byte 255, whose window ends at n) one slot short; the table's spare capacity holds a sentinel, read back to catch any write at or past n |
| `b5_top_byte_and_largest_block` | byte 255 at every position, and the largest block `new` accepts (2^24 − 1 rows of byte 255: the top entry `0xFFFF_FEFF`, no carry), against `bwt::build` at k 1 to 4; 2^24 rows refused |
| `b5_lying_counts_fuzz` | 3,000 run-heavy columns with lying counts and checkpoints, both share orders: `bwt::build`'s table or a refusal, never a write past n, never a panic |

- **Applied** from the reviewer's diff, the same as commit `6ac4725f5` against `31355857`, onto
  `89d589ba`.
- **Two mechanical changes,** so that CI's `cargo fmt --all --check` and
  `cargo clippy --all-targets --all-features -- -D warnings` pass:
  - `cargo fmt` reformatted three places;
  - one indexed loop over the sentinel slots (`for s in n..n + 32`, flagged by clippy's
    `needless_range_loop`) became an `enumerate().skip(n)` with the same assertion.

  No test logic changed.
- **Result:** `cargo test --release --lib coop::` passes 27 of 27, the three new tests
  included. clippy and fmt are clean.
- **The laxer guard is now caught natively.** The `s + 15 > lim` mutant, run once more
  against this suite, fails `b5_guard_top_bucket_sentinel` and `b5_lying_counts_fuzz`. The
  original record stands: the mutant survived the implementer's native tests (§2, §8).
- **Unchanged:** the kernel, the count and the dispositions. Condition 3 remains
  **FAIL-MEASUREMENT** (D085).
