# 2026-10-27: The bz2 decoder bake-off: is an existing decoder already as fast as ours?

The compute-frontier entry (#194) built a prototype bzip2 decoder, `bz2k`. It walks the
inverse BWT as 12 interleaved chains, with a PCLMULQDQ CRC and AVX2 RLE1 and MTF, and
measured 1.76× lbzip2 on one thread. Its production form is **mibz2**, the in-repo crate
of branch `bz2-native-decoder` (provisionally named `bunzip`; benched at ed06991).

Before investing further, this entry asks whether an existing decoder is already as fast:

- pbz2 (Rust);
- fbz (Rust and Python);
- the `lbzip2` crate (pure Rust);
- indexed_bzip2 (C++, Python bindings);
- lbzip2 (C, today's production decoder);
- libbzip2 (C, and its Rust port libbz2-rs-sys).

All of them were run on the same files, through the same sink, on this machine.

**The answer: one is. pbz2 0.2.0 ties mibz2** on both wall and total CPU, at 1 thread and
at 4. Both are about 1.85× lbzip2 `-n4` on wall and about 2× on CPU. Every other
contender is slower than lbzip2 or level with it.

pbz2 independently uses the same core idea: a segmented, multi-chain inverse-BWT walk.
We are building mibz2 to be the best bzip2 decoder we can make. So pbz2 is the reference
implementation to learn from and to beat. Its techniques worth trying in mibz2 are listed
below.

## The protocol

- **Inputs:**
  - **(b) the bench slice:** the quick tier's `custom-ci-quick-slice.json.bz2`, 79,247,269
    B, 1,084,929,419 B out. It is the exact file of #194's 1.76×.
  - **(a) real dump blocks:** 8 windows of 8 MiB at (i + 0.5)/8 of `latest-all.json.bz2`.
    - `harness/mkstream.py` keeps each window's whole blocks, their encoded bits
      untouched, as one stream per window. It adds a "BZh9" header, the end marker and
      the combined CRC.
    - That gives 66,710,819 B, 8 streams and 3,174 blocks, decoding to 1,473,300,225 B.
    - `bzip2 -t` passes.
- **One command per decoder,** writing the decoded bytes to stdout:
  - `harness/src/main.rs` (`bakeoff DECODER THREADS FILE`) wraps the Rust crates;
  - `harness/ib.py` wraps indexed_bzip2;
  - lbzip2 and bzip2 are their own CLIs.
- **The sink (`harness/run.py`):**
  - a 1 MiB pipe read by the runner;
  - round 0 hashes the output (sha256, in the runner, so the hash's CPU is not the
    decoder's); rounds 1.. discard it;
  - each run records wall time (spawn to exit), time to first output byte, the child's
    user+sys CPU and peak RSS (`wait4`), and the exit code;
  - the 1-minute load and the steal share (`/proc/stat`) are recorded around every run.
- **Rounds** are interleaved round-robin across decoders, so drift falls on everyone
  alike. The one exception is the first slice batch, run before drift was noticed.
- **Threads:** 1-thread runs are pinned to one CPU (`taskset -c 1`), so a decoder's helper
  threads share its core. 4-thread runs are not pinned.
- **APIs:** each crate's own single-thread API at 1 thread, and its parallel API with an
  explicit thread count at 4. The `lbzip2` crate has no thread count: it takes the CPUs
  it may run on, so the pin decides.
- **Units:**
  - c/B is cycles per decompressed byte at the 2.1 GHz TSC: wall c/B = wall × 2.1e9 /
    bytes; CPU c/B = (user+sys) × 2.1e9 / bytes;
  - the paired ratios are geometric means of per-round ratios, with t intervals.
- **The machine:** 4 cores (Intel Xeon, AVX2 and AVX-512, no SHA-NI), 1 thread a core,
  L2 1 MiB a core and L3 33 MiB shared (lscpu), 15 GB RAM.

### Why CPU at 4 threads exceeds CPU at 1

The premise needs one correction. At 4 threads, both decoders' CPU is below 4× their
wall: pbz2 25.7 CPU-s over 7.89 s is 3.3×, and mibz2 29.5 over 8.44 is 3.5×. What rises
is CPU against the 1-thread run: pbz2 19.9 → 25.7–29.7 and mibz2 18.7 → 29.5–31.8, about
1.3–1.6×.

- **The threads** (`/proc/PID/task` during a 4-thread slice decode, CPU ticks so far):
  - **pbz2:** the main thread (the caller's `read`: in-order assembly, about 4.5% of the
    process's CPU), 4 workers (`pbz2-0..3`) and 1 input reader (under 1%). So N workers +
    1 reader, as believed, plus the consuming thread.
  - **mibz2:** the main thread (under 1%), 4 workers (`bunzip-0..3`), `bunzip-scan` (each
    block's Huffman decode, the one sequential phase: about 8%) and `bunzip-read` (under
    1%). So N workers + 1 scanner + 1 reader.
  - **Neither duplicates work.** mibz2's Huffman decode happens once, in the scanner, and
    the auxiliary threads are 5–9% of the total.
- **The rest is per-worker slowdown when 4 walks share the memory system** on this VM.
  lbzip2 shows the same rise (49.0 → 59.8 CPU-s), and #194 measured none on a quieter
  day ("per-thread cost kept at 4 threads").
  - So it is a property of the box under its neighbours, not of either decoder.
  - The split's other work would see it too.

### How each one walks the inverse BWT

| decoder | the walk |
|---|---|
| **mibz2** (and bz2k) | 12 lanes over 256 pseudo-random segment starts. A 112 KB bitmap marks the starts, and each lane takes the next segment when its own ends. Segments go into per-segment buffers and are joined in text order. A repeated-string block (several cycles) falls back to the plain walk. |
| **pbz2** | **The same idea, found independently** (`pbz2-core/src/block.rs`, `walk_in_pieces`). 16 lanes over 128 evenly spaced starts plus the origin. A start is marked by bit 31 of the T-vector entry itself, so there is no separate bitmap. Pieces go into a paged arena of 1 KiB pages (linked by a `u16` next-page table, about 1 MB in all), are joined stop to start, and are packed back over the T-vector. Blocks under 64 KiB, or whose pieces don't join (periodic text), go to `walk_whole`. |
| fbz | one chain, fused with RLE1 (safe indexing) |
| `lbzip2` crate | one chain, raw pointers, fused with RLE1 |
| indexed_bzip2 | one chain, fused with RLE1 and the byte-at-a-time CRC (micro-bunzip lineage) |
| lbzip2 (C) | one chain, fused with RLE1 and the CRC (`emit`) |
| libbzip2 | one chain |

So **pbz2 is the only other decoder doing memory-level-parallel walking**, which is why it
is the only one level with mibz2. The others are 1.5–1.9× slower on the real blocks, which
is about where a single-chain walk sits.

### pbz2's techniques worth trying in mibz2

Each is a candidate for mibz2's own bench, not a measured gain:

1. **Stop flags in the T-vector entries instead of a bitmap.**
   - An entry is 8 bits of byte plus a 20-bit index, so bits are spare.
   - The lane's own load already brings the flag, so there is no second load to a 112
     KB bitmap at each step.
   - The cost: the start entries are dirtied, and cleared or ignored after the walk.
2. **The paged arena for the pieces.** Pages handed out from one arena, linked by a small
   next-page table. Lanes never grow a `Vec` and there is no per-segment allocation, so
   the memory is bounded: one T-vector plus the arena.
3. **The 4-lane interleaved T-vector build** (`link`). It counts and scatters over 4
   quarters of the block at once, so the scatter's cache misses overlap. #194 left the
   build at 5.8 c/B, "not tried".
4. **Two symbols per Huffman refill** (`SYMBOLS_PER_FILL = 2`). #194 put multi-symbol
   decoding at ≤ 1 of the Huffman phase's 1.9 c/B.
5. **A `walk_whole` fallback by size and by failed join:** blocks under 64 KiB skip the
   segmentation's setup cost.
6. **Its lower memory:** 16 MB peak at 1 thread against mibz2's 33, and 34 MB at 4
   threads against 99.
   - pbz2's scratch is one block's words plus the arena: `decode_scratch_words`, about
     4.6 MB at level 9.
   - mibz2 holds more blocks in flight (2 × threads slots) and per-segment buffers.
7. **The MTF list's front 8 bytes held in a `u64`** (a SWAR find-and-shift), with SIMD
   only past it. It also gives a portable fast path for aarch64, where mibz2 has only
   scalar code today. Likewise pbz2's 8-bytes-at-a-time RLE1 (`copy_without_runs`) as
   the portable twin of the AVX2 one.
8. **Evenly spaced starts plus the origin:** pbz2 does not show the clustering #194 saw.
   - #194 rejected evenly spaced starts because they clustered in the text and stalled
     lanes.
   - pbz2 uses evenly spaced *rows* with 16 lanes and 128 starts, and is level with
     mibz2.
   - A sweep of lanes × starts × spacing on mibz2's bench would settle it.
9. **Randomised blocks:** pbz2 decodes them (a 512-entry table, about 30 lines);
   mibz2 refuses them. Only bzip2 ≤ 0.9.0 wrote them, so this is completeness, not speed.

In the other direction, what mibz2 has that pbz2 lacks:

- runtime-dispatched PCLMULQDQ CRC and AVX2 RLE1/MTF in a baseline build;
- error positions (block, bit);
- no dependencies.

pbz2's `native` build measured no gain from compile-time AVX2/PCLMUL, so these are
features rather than a speed margin on this box.

## The verdict

- **Is an existing decoder faster than ours on Wikidata blocks?**
  - **No decoder is faster than mibz2.** pbz2 ties it at 1 thread (0.98, 0.90–1.06) and
    at 4 (1.00, 0.86–1.16 on the slice; 1.06, 0.77–1.46 on real blocks), on CPU as on
    wall.
  - **Everything else is slower:** fbz, the `lbzip2` crate, indexed_bzip2, lbzip2 and
    libbzip2 are 1.5–2.0× slower in wall and up to about 2× in CPU on real blocks at 4
    threads.
- **Uncertainty:**
  - the intervals on a drifting shared VM are ±10–15% at 4 threads;
  - a gap under about 10% either way would not show;
  - the second machine (CI) was not used.
- **The direction (the user's):** keep building mibz2, the best bzip2 decoder we can make.
  - pbz2 is the competitor and the reference implementation.
  - Its walk confirms the design: the gain is the multi-chain walk, and an independent
    implementation arrived at the same speed.
  - The list above is where it might be beaten: the T-vector flags, the arena, the 4-lane
    build, two symbols a refill, memory.
- **Correctness:** both are byte-identical to libbzip2 on everything run here, and both
  error on every damage tried.

## Reproduce

Everything is under `2026-10-27-bz2-bakeoff/harness/`:

| file | what |
|---|---|
| `Cargo.toml`, `src/main.rs` | `bakeoff DECODER THREADS FILE`: each Rust decoder to stdout. Needs mibz2's crate at the repository root as `crates/bunzip` (branch `bz2-native-decoder` @ ed06991: `git archive ed06991 crates/bunzip \| tar -x`). |
| `ib.py` | indexed_bzip2 to stdout (`pip install indexed_bzip2==1.7.0`) |
| `mkstream.py OUT WINDOW...` | real dump windows (`curl -r`) to a valid .bz2 of their whole blocks, bits untouched |
| `mkdata.sh DIR` | Silesia, repetitive text and seeded random data, each `bzip2 -9` (generated; their timing moved to mibz2's own harness) |
| `run.py OUT WORKLOAD FILE THREADS DECODER...` | the timing: interleaved rounds, a hashed round 0, wall, CPU, peak RSS, time to first byte, load and steal per run (`BAKEOFF_BIN`, `BAKEOFF_BIN_NATIVE`, `BAKEOFF_PY`, `REPS`) |
| `summarize.py`, `paired.py` | the tables, and the paired ratios with 95% intervals |
| `robust.py GOOD.bz2 TRUTH OUT` | the damaged inputs and every decoder's verdict |

`results/` holds the raw records, one JSON line per decoder × batch, with every run:

- `slice_pass1.jsonl`: the first slice batch;
- `slice_rr.jsonl`: the interleaved slice batch;
- `real_4t.jsonl`: real blocks at 4 threads;
- `native.jsonl`: pbz2's native build;
- `robust.jsonl`: the robustness checks.

Scratch paths are shown as `SCRATCH/`.
