# 2026-10-27: A native bz2 decoder for the split, behind a flag: byte for byte lbzip2's, its decode 1.4–2.3x faster, the split's CPU −20% on CI

#194 (docs/journal/2026-10-27-compute-frontier.md, section 2) found that the bz2 decode
is about half of the split's CPU. It also found that the decode is bound by the inverse
BWT's chain of dependent loads, not by bandwidth. Its prototype (`kernels/bz2k`) decoded
at 24.3 c/B against lbzip2's 42.7. This entry turns that prototype into a
production-quality decoder in `reshape`:

- block-parallel, as lbzip2 is;
- portable, with SIMD chosen at run time;
- validated against libbzip2 and lbzip2 on real Wikimedia blocks, malformed input and a
  fuzz loop;
- selected in the split by `WIKIDATA_BZ2_DECODER=native`. **lbzip2 stays the default.**

PR #197. **Measured** figures are this machine's (a shared 4-core VM, so indicative only)
or CI's paired bench. **Modelled** figures scale them to a release, and say what they
assume.

- **Threads, for the coordinator to reconcile with the writer's pool:** the native

  decode's CPU. So the split now holds 4 + 1 decoder threads, its 2 workers and the
  writer's rayon pool. The decode now takes half the CPU it did, so the best split of
  threads probably moves. That is not tuned here.

## Design

### The module and its API

`crates/bunzip/src/` (its Python class is reshape's `bz2_py.rs`):

| file | what |
|---|---|
| `bits.rs` | MSB-first bit reader; past the input's end it reads zeros and says so (`overran`) |
| `block.rs` | phase 1: a block's header, selectors, code tables and Huffman symbols, with libbzip2 1.0.8's checks |
| `mtf.rs` | phase 2: RUNA/RUNB and move-to-front (scalar; AVX2) |
| `bwt.rs` | phases 3-4: the T-vector and the walk, behind `InverseBwt` |
| `rle.rs` | phase 5: RLE1 (scalar; AVX2) |
| `crc.rs` | CRC-32/BZIP2 (slice-by-8; PCLMULQDQ) |
| `stream.rs` | streams in order: headers, blocks, end markers, combined CRCs, from a `Source` |
| `parallel.rs` | the threaded streaming decoder |
| `read.rs` | `BzReader` (a `Read` adaptor, sequential or parallel) and `scan` (block boundaries) |
| `lib.rs` | `Kernels`, errors, `decode_block`, `decode`, `decode_parallel`, `decode_blocks` (a range) |

- **`StreamDecoder`** (Python: `Bz2Decoder(threads, slots=None)`):
  - `write(bytes)` blocks while the input queued is full.
  - `close()` ends the input.
  - `readinto(buffer)` returns decoded bytes, in order.
  - `cancel()`, and `join()`.
  - It behaves like a decoder process's two pipes. A write after the decode has stopped
    raises `BrokenPipeError`, as a pipe's writer gets.
- **`decode_blocks(data, start_bit, end_bit, level, kernels, out) -> Range`:**
  - decodes the whole blocks from a block header's bit to the next block's (or to a
    stream end marker);
  - checks each block's CRC;
  - returns each block's bit range and CRC (and the stored combined CRC where the range
    meets its stream's end), so a caller can check its stream's CRC with `combine`.
- **`decode(data)`:** sequential, a whole .bz2. It is the tests' reference.
- **`bwt::InverseBwt`:** the inverse-BWT kernel interface: a block's last column (and its
  byte counts) and primary index in, its RLE1-coded text out, with the kernel's own
  buffers kept from block to block.
  - It covers table construction, any preprocessing, the walk and the joining. So a
    kernel with its own table (an LF² pair table, say) fits behind it, and timing the
    whole decoder with a kernel (`decode_with::<I>`, `StreamDecoder::with_inverse::<I>`,
    `bzcat` with `BZ2_INVERSE=plain`) includes all of its costs.
  - Nothing in it is specific to Wikidata or to this pipeline.
  - Two kernels exist: `Segmented` (the default) and `Plain`, the plain walk, which
    every test checks the default against.

### Decoder-agnostic integration

The split's side does not depend on this decoder. A bake-off of existing decoders (pbz2,
fbz, the lbzip2 crate, indexed_bzip2) is under way elsewhere, so any in-process Rust
decoder can take this one's place as a backend swap:

- **`reshape/src/bz2_py.rs`:** `Bz2Decoder(threads, slots=None, backend="native")`
  wraps a `Backend` trait with seven methods: `write`, `close`, `read`, `cancel`, `join`,
  `threads` and `describe`. `native` (this crate's `StreamDecoder`) is its one
  implementation. Another backend is an `impl Backend` and a name in `backend()`.
- **`dump.py`:** `IN_PROCESS_BZ2` maps each `WIKIDATA_BZ2_DECODER` value to a backend:
  `{"native": "native"}`. `_in_process_lines` feeds and reads every backend the same
  way, so the restart contract and the follow-the-download path are the same for all.
- **The split's checks take the decoder's name:**
  - `scripts/test_split_bz2_decoder.py SLICE [DECODER]` (byte identity, the three restart
    cases, a corrupted dump);
  - the bench stage (`BENCH_BZ2_DECODER`, default `native`, recorded as
    `bz2native_decoder`);
  - `WIKIDATA_BZ2_DECODER=… scripts/test_split_follow.py`.
- **The Rust harness checks any decoder behind `Candidate`** (`crates/bunzip/tests/
  common`: `name`, `decode`), with libbzip2 as the oracle. That covers the fuzz loop
  (`examples/fuzz.rs`) and the real-window check (`examples/windows.rs`). Another decoder
  is a `Candidate` impl (and a dev-dependency) in `candidates()`.
  - The crafted- and malformed-stream suite (`tests/decode.rs`) also checks this crate's
    own error kinds. Its oracle comparisons carry over; its kind assertions do not.

### Threads and memory

- **A scanner thread** reads the stream in order: each block's header and its Huffman
  symbols, and each stream's header, end marker and combined CRC.
  - This is the one phase that must be sequential: a block's end is known only once its
    symbols are read.
  - It is about 1.6–1.9 c/B of the decode's ~24–30, so one scanner feeds about 12
    workers before it binds.
  - It finds blocks exactly, not by searching for the 48-bit magic, so a magic inside
    a block's data can never be taken for a block.
- **`threads` workers** each finish a block: phases 2–5 and the block's CRC check.
- **The reader** takes blocks in order. A block's error reaches the reader only once
  every block before it has been read, so the bytes read before an error are exactly
  the stream's up to that block.
- **Memory is bounded:**
  - at most `slots` (default 2 × threads) blocks between the scanner and the reader;
    the scanner waits for a slot;
  - a slot holds a block's symbols (≤ 1.8 MB) and its decoded bytes (~1 MB of JSON;
    ≤ ~46 MB for a block of runs only);
  - each worker keeps ~7 MB of buffers;
  - the input held is 2 queued chunks (the split writes 8 MB at a time) and the
    scanner's window from the block it is reading. Its lookahead starts at 2 MB and
    doubles for a longer block, up to 64 MiB.
  - Buffers are reused from block to block.
  - **Measured:** 113 MB peak RSS decoding alone at 4 threads, against lbzip2's 34 MB.
- **In the split, peak RSS rose by +38 to +239 MB** a run (quick slice: 2,649 → 2,814 MB
  on average over 3 runs; real lines: 1,434 → 1,561 MB over 2).
  - The decoder's own share is about +80 MB.
  - The rest is likely the split holding more chunks at once, because the decode now
    runs further ahead of the split's 2 workers. That is still within the split's own
    bound (`MAX_PENDING_BYTES`, 4 GiB of lines).
  - Not separated further here. On a 16 GB laptop it is small.

### Kernels and dispatch

- **`Kernels::detect()`** runs once per decoder:
  - AVX2 (with BMI1): the move-to-front of an index below 32 as one blend, and RLE1's
    4-equal-bytes test at 32 positions at once;
  - PCLMULQDQ (with SSE4.1 and SSSE3): the CRC, 4 lanes folded 512 bits at a time.
- **Each kernel has a scalar twin,** used on any other CPU and on aarch64.
  `WIKIDATA_BZ2_SIMD=off` forces the scalar kernels (in the split too), and every test
  runs both sets.
- **No `target-cpu`:** the extension is built for the x86-64 baseline, as before.
- **The walk's gain is scalar code** (memory-level parallelism), so ARM keeps it.
  NEON/PMULL twins of the three small kernels are not written. The scalar fallback alone
  is 1.5× lbzip2 on real blocks (measured).
- **aarch64:**
  - the decoder's tests and a fuzz run pass under qemu;
  - the whole `reshape` extension cross-builds for `aarch64-unknown-linux-gnu`.
  - No ARM hardware was timed.

### The walk, and prior work

- **The default kernel** (`bwt::walk_segments`) walks the list as 12 interleaved chains:
  - 255 pseudo-random rows plus the walk's first row are segment starts;
  - a bitmap of the starts ends each segment;
  - each lane takes the next segment when its own ends;
  - the segments are joined in order from the first row's.
- **It equals the plain walk on every list,** several cycles included. The join follows
  the segments' links until the block's length is reached, which by construction gives
  the plain walk's first n steps. So it needs no fallback.
- **Blocks under 64 Ki** are walked plainly.
- **The idea is not new.** Kärkkäinen, Kempa and Puglisi, "Slashing the Time for BWT
  Inversion", DCC 2012, pp. 99–108, interleave several traversals of one inversion on
  one thread, so that out-of-order execution keeps their loads in flight.
  - They add a super-alphabet (an LF² table: two characters per dependent lookup) and
    "Precopy" for repetitive data. Neither is implemented here.
  - What is particular here is only how the traversals are found in an existing bzip2
    file, which carries no extra metadata for it: the random segment starts, the stop
    bitmap, and the joining in order.

### The format, and its choices

The decoder makes libbzip2 1.0.8's checks (`decompress.c`), in the same terms:

- the stream header (`BZh` and a level 1–9);
- block and end magics;
- `origPtr` (against 10 + 100,000 × level, then against the block's length);
- symbols in use;
- 2–6 tables;
- at least 1 selector, those past 18,002 read and dropped;
- each selector below the number of tables;
- code lengths of 1–20;
- Huffman codes decoded by libbzip2's own limit/base/perm tables, so an incomplete code
  behaves exactly as there;
- the symbols outrunning the selectors;
- a run's weight below 2^21;
- the block no longer than its level allows;
- a block ending inside an RLE1 run (4 equal bytes and no count byte), which libbzip2
  refuses because it reads a count past the block's end;
- every block's CRC, and every stream's combined CRC.

Its own choices, each a clear error of its own:

- **Randomised blocks** (written only by bzip2 0.9.0 and earlier, before 1999) are
  refused: "not supported by this decoder".
- **Bytes after the last stream that do not begin another stream** are an error.
  lbzip2 and bzip2 ignore them. Refusing them means nothing after a stream is ever
  silently dropped. The real dump ends exactly at its stream's end (the tail window).
- **An oversubscribed Huffman code** whose code points past the alphabet (where libbzip2
  reads a stale table entry) is an error.
- **A block whose compressed form passes 64 MiB** is an error. A real block is at most
  ~4.2 MB; only a code-length table padded with no-op steps could be longer.

**Panics:** a worker's panic is caught and becomes an error. None was seen in a million
fuzz cases with overflow checks on.

**`unsafe`:** the SIMD kernels, the walks' unchecked loads (every link in a `TVector` is
below its length by construction: `build` assigns links rather than adding them), and
the Python buffer write.

### The split

- `_dump_lines` delegates to `_in_process_lines` when the flag is on and the dump is bz2.
- **The feeder is the same `_feed` thread.** It writes the dump (or its download as it
  is written) into `Bz2Decoder.write` as into lbzip2's stdin, and it closes it at the end.
- **The lines are read through an `io.BufferedReader`** of 16 MiB over the decoder, as
  lbzip2's stdout is read. So the lines, and the chunks cut from them, are the same.
- **On a bad stream,** the reader raises `RuntimeError("native bz2 decoder: bz2 data
  error: … (block N, at bit B = byte b)")`, once every line before that block has been
  given. lbzip2's path raises `RuntimeError("lbzip2 exited with 1")`.
- **When the split stops reading early** (a worker's error), closing the reader cancels
  the decoder. The feeder's next write then fails as a closed pipe's, and the feeder
  ends.
- **Restart is unchanged:** a rerun decodes the dump from its start and skips the chunks
  already in `manifest.split.jsonl`. The decoder is deterministic, so the chunks are the
  same whichever decoder ran before.

## Correctness evidence

**Real Wikimedia blocks** (`crates/bunzip/examples/windows.rs`):

- **The method.** In each window, the first block magic at any bit is found. From there
  the blocks are read block after block, each decoded with its CRC checked. The whole
  blocks are then written as a stream of their own: a header, their bits, an end marker
  and their combined CRC.
- **Every decoder agrees.** That stream decodes to exactly the blocks' bytes in
  libbzip2, lbzip2 (`-dc -n4`), this decoder (scalar and SIMD, sequential and parallel),
  and `decode_blocks` on the window's own bits.
- **The result:** 14 windows, 1,885 blocks, 954,210,972 bytes, all identical.
- **The dump's shape:**
  - The dump is one stream. The tail window's end marker and CRC end exactly at the
    file's end.
  - The head window starts `BZh9`.
  - Blocks decode to 0.5–0.9 MB of JSON each.

**Tests against libbzip2** (`crates/bunzip/tests/decode.rs`). libbzip2 here is the
bzip2 crate's bundled 1.0.8. Each test runs on both kernel sets, sequential and parallel:

- valid streams at levels 1, 2, 5 and 9 of 11 shapes (text, runs of every length,
  random, two letters, zeros, `ab` and `abc` repeated, all bytes, empty, one byte);
- the parallel decoder fed and read in every chunking, from a byte at a time to 8 MiB,
  with 1–8 threads and 1–16 slots;
- multi-stream input (an empty stream among them);
- 300 crafted blocks from a block writer, with any primary index: random last columns
  (lists of several cycles among them), runs ending blocks, and blocks of 1 to 900,000
  bytes. Each is checked against libbzip2, against a plain reference implementation,
  and against the `Plain` kernel. Those that end inside a run are refused by both;
- **block-size headers 1–9:** a block of exactly 100,000 × level decodes and one byte
  more is refused; and a real stream's header lowered below its blocks' size is refused;
- **oversized runs:** RUNA × 22 (the weight reaches 2^21) is refused as libbzip2 does.
  RUNB × 20 is under that weight but longer than the block, and is refused too. A
  900,000-byte single run decodes;
- `origPtr` at the block's length and past the level's bound; an empty block; no
  symbols; symbols outrunning their selectors;
- **randomised blocks:** refused, sequential and parallel;
- **block CRCs:** a bit flipped in every block's stored CRC. That block fails, after
  every block before it, at the right bit;
- **the stream CRC:** a bit flipped in the stored combined CRC;
- **truncation** at every 997th byte and the last 12;
- **trailing bytes** (`x`, `\0`, `BZ`, `BZh`, `BZh0`, `BZhx`, `garbage`) after a stream,
  and a lone `BZh9`; an empty input; and a non-bz2 input;
- **every bit of the first block's header and code tables flipped** (3,000 bits): libbzip2
  and this decoder both fail, or both give the same bytes;
- **block boundaries:** every range of whole blocks of a level-1 stream decoded alone by
  `decode_blocks`, each exactly its part of the stream. A range ending inside a block
  fails;
- **the reader stopping mid-stream:** the writer's next write fails, and nothing hangs.

All 13 pass on x86-64 (AVX2 and scalar), and on aarch64 under qemu-user (scalar).
`tests/corpus.rs` adds corpora that are not Wikidata's, decoded by every public entry
point (below).

**Fuzz** (`crates/bunzip/examples/fuzz.rs`, built with overflow checks and debug
assertions):

- **The corpus:** valid streams of the shapes above at levels 1 and 9, crafted blocks,
  and a multi-stream file.
- **The mutations:** 1–4 each of bit flips, byte sets, cuts, inserts, deletes and splices,
  mostly in the headers and tables.
- **Each mutant** is decoded by libbzip2 and by this decoder, on alternate kernel sets,
  and every 16th also in parallel (which must equal the sequential decoder).
- **The results:**

  | run | cases | failures | both decode, same bytes | both fail | libbzip2 decodes, this refuses |
  |---|--:|--:|--:|--:|--:|
  | x86-64, 15 min | 988,256 | **0** | 3,896 | 984,260 | 100 (all `Randomised`) |
  | aarch64 (qemu), 3 min | 32,585 | **0** | 113 | 32,469 | 3 (all `Randomised`) |
  | x86-64, 1 min (first) | 82,674 | **0** | 371 | 82,299 | 4 (all `Randomised`) |

  - **The randomised cases:** the mutation set a block's randomised bit. For a block
    shorter than libbzip2's first randomisation offset (618 bytes), de-randomising
    changes nothing, so libbzip2's CRC still passes.
  - **Both decoders' errors spread over every kind:** bad magic 15%, code lengths 12%,
    truncation 13%, block CRC 12%, and so on. So the mutations reach every check.

**The split** (`scripts/test_split_bz2_decoder.py`, the quick tier's slice; and
`bench/bz2native.py` on real dump lines):

- every file both ways the same, byte for byte: 68 on the slice, and 206 on 80,071 real
  dump lines (954 MB of JSON from the windows, recompressed by lbzip2);
- a split killed after 2 chunks and run again, with native → native, lbzip2 → native and
  native → lbzip2: every file the same as an uninterrupted lbzip2 split;
- a corrupted dump (a byte flipped mid-file): exit 1 both ways. The native split
  names "block CRC mismatch … (block 504, at bit 316,278,752)";
- `scripts/test_split_follow.py` with the flag on: the split following the download (5
  cases, a killed download among them) gives the same chunks. A download failing its
  md5 stops the split, and its chunks are deleted;
- `scripts/test_split_errors.py` with the flag on: a worker's error ends the split with
  its traceback, exit 1, and the decoder stopped behind it.

## The release, modelled

- **The bench's release model:** the split is CPU-bound at 30–120 MB/s. Its ETA is its
  CPU a byte of the slice's bz2, scaled to the dump over 4 cores: 2h52m30s on this PR's
  run (CI's runners; #194 quotes 3h20m from master's records). At 7 MB/s the uploads
  bind.
- **The assumption:** the split's wall at a release falls by the split's measured CPU
  change. #194's real-data model says a release's split is more CPU-bound than the
  bench's, so this is if anything conservative.
- **On CI's figure,** −20.5% of the split's CPU is **−35 min of the release at 30–120
  MB/s (modelled):** the bench's split ETA is 2h52m30s on this run. Below #194's −46 min,
  because the decode itself gained 1.43× on CI, not 1.76×.
- **On this box's figures** (−30% to −37%), it would be −52 to −64 min.
- **Nothing at 7 MB/s:** a CPU-efficiency win there, not a wall one.

## A standalone crate

The decoder is a crate of its own, `crates/bunzip`, so it can serve programs that know
nothing of Wikidata, and so it can later move to its own repository by moving the
directory.

- **No dependency** beyond std. Its dev-dependency is the `bzip2` crate (libbzip2
  1.0.8, the oracle and the test encoder).
- `reshape` depends on it by path (`bunzip = { path = "../crates/bunzip" }`).
  - The Python class (`reshape/src/bz2_py.rs`), the `WIKIDATA_BZ2_*` variables and
    the split's integration (`dump.py`) stay outside it.
  - `reshape/pyproject.toml`'s uv cache keys take in the crate's sources, so an edit
    there rebuilds the extension (checked).
  - The bench workflow now also runs on `crates/**`.
- **Its public API, for ordinary bzip2 data:**
  - `decode(data)` and `decode_parallel(data, threads)`;
  - `BzReader::new(r)` and `BzReader::parallel(r, threads)`, a `Read` adaptor;
  - `StreamDecoder`, the push form, with an explicit thread count and in-flight bound;
  - `scan(data)` (block boundaries, nothing decoded) and `decode_blocks` (a range of
    whole blocks): the entry points the sweep reader could use;
  - `Error`, `ErrorKind`, and `From<Error> for io::Error`;
  - `Kernels`, and `bwt::InverseBwt`.
- **Its tests run on their own** (`cargo test --release`): `tests/decode.rs` (above) and
  `tests/corpus.rs`.
  - `tests/corpus.rs` uses corpora that are not Wikidata's, each compressed by libbzip2
    at levels 1, 6 and 9: its own sources as text, random bytes, one byte repeated, a
    7-byte pattern, runs of random lengths, and binary records.
  - Each is decoded by `decode`, `decode_with` (the scalar kernels and the plain walk),
    `decode_parallel`, `BzReader` (both forms), and `scan` with `decode_blocks`.
  - It also covers a source giving 1–7 bytes a read, a failing source (its own error
    comes back), and a bad stream (`InvalidData` wrapping `bunzip::Error`).
- **`cargo bench`** times the same corpora, larger: libbzip2 against this crate (SIMD,
  scalar and plain walk on one thread; every core). Its README discloses the machine.
  On this shared VM, at 2.8 GHz nominal:

  | corpus | ratio | libbzip2, 1 thread | bunzip, 1 thread | plain walk, 1 thread | bunzip, 4 threads |
  |---|--:|--:|--:|--:|--:|
  | text (sources) | 19.8× | 34 MB/s | 84 | 17 | 155 |
  | random | 1.1× | 8 | 31 | 17 | 89 |
  | pattern (7 bytes) | 17,563× | 139 | **93** | 210 | 302 |
  | runs | 263× | 250 | 1,434 | 797 | 666 |
  | binary records | 1.0× | 8 | 32 | 9 | **31** |

  Two weaknesses show, both outside Wikidata's data:
  - **A short pattern repeated** is 0.67× libbzip2 on one thread. Its walk is
    cache-resident and prefetchable, so the plain walk wins, and the segments only cost.
    Choosing the kernel per block is open work for the walk research behind
    `InverseBwt`.
  - **Incompressible records do not scale past one thread.** The sequential Huffman
    scanner is most of their decode.
- **The README** covers usage, the API, the format's choices, prior work (libbzip2's
  format and checks; Kärkkäinen, Kempa and Puglisi, DCC 2012; lbzip2 and pbzip2's block
  parallelism) and the benchmark's disclosure.
- **What an extraction would need:**
  1. **A licence.** The repository declares none, so the crate declares none, and its
     owner must choose one.
  2. **A name.** `bunzip` is provisional; it is unchecked on crates.io.
  3. **Its own CI:** `cargo test` on x86-64 and aarch64 (qemu or an ARM runner), a
     fuzz job, and `cargo bench`.
  4. **wikidata-pq:** move `crates/bunzip`, and point reshape's dependency at the new
     repository (git or crates.io). Then drop the cache keys and workflow path, or point
     them at the new location.
  5. **Optionally:** `#![no_std]` + `alloc` for the sequential decoder, and the crate's
     `Cargo.lock` dropped, as a library's usually is.

## The sweep reader (#185), later

#185 decodes block-aligned segments of the dump with an `lbzip2 -n1` subprocess each. Its
segments' boundaries are found by its own probes. `bunzip::scan(data)` finds every block's
bit range, its stored CRC and its stream's level without decoding (Huffman symbols only).
`bunzip::decode_blocks(data, start_bit, end_bit, level, kernels, out)` is the in-process
equivalent of a segment's `lbzip2 -n1`:

- it decodes the whole blocks from one block header's bit to the next's;
- it checks each block's CRC;
- it returns each block's bit range and CRC, so the caller can combine a stream's CRC
  across segments (`bunzip::combine`).

The hookup:

- **Expose `decode_blocks` to Python,** or to a Rust sweep reader, over a memory-mapped
  or read range of the dump.
- **Keep the segment-level parallelism #185 already has**, one segment per thread, with
  the parallel decoder's slots as the bound. Or feed a segment's bytes to a
  `StreamDecoder` started at a block.
  - A `Source` that starts mid-stream would be a small addition: a scanner state that
    begins at a block with a known level.
- Not done here. #185's branch and its `reshape/src/bz2.rs` were neither touched nor
  depended on.

## Before it could be the default

1. **The gain on 2-core SMT machines** (CI's runners: 1.43× on the decode, against 2×
   here). Measure it on a laptop's own cores: is it the SMT siblings or the CPU?
2. **One whole dump through it:** every one of a release's ~3.3 million blocks (about
   1.8 TB of JSON; the windows held 135 blocks a 4 MiB) against lbzip2, and the release's split timed. The full-dataset tool
   (`bench/full/`, another agent's) reads `WIKIDATA_BZ2_DECODER` for this.
3. **The thread split,** with the writer's pool capped (another PR): the decoder's
   threads (`WIKIDATA_BZ2_THREADS`) against the split's workers and rayon's.
4. **Peak RSS** (+3–16% a run in the split here): separate the decoder's ~80 MB from the split
   holding more pending chunks, and fewer slots, if it matters.
5. **ARM hardware:** timed on a real aarch64 laptop. Only correctness under qemu was
   checked here. Optionally NEON/PMULL kernels.
6. **A review of the `unsafe` code** (listed above), and a longer fuzz run (cargo-fuzz
   with coverage guidance, not just this mutation loop).
7. **The scanner's bound:** one sequential Huffman thread feeds about 12 workers. That
   is enough for 4–8 cores, not for a 16-core machine.

## Uncertainty

- **Local timings are on a shared VM** with other agents' jobs running (load average
  2–5). lbzip2 itself ran 1.3–1.5× slower here than in #194. The ratios repeat across
  runs; the absolute figures don't transfer. CI's paired bench is the authority.
- **The split's measured CPU fell more than #194's model predicted** (−30 to −37% against
  ~−23% from 53.5% × (1 − 1/1.76)). This may be less oversubscription, or noise. CI will
  tell.
- **The real-lines split recompresses the windows' text with lbzip2 -9.** Its blocks are
  lbzip2's, not Wikimedia's. The decode alone was timed on Wikimedia's own blocks.
- **The fuzz loop is a mutation loop, not coverage-guided,** and it starts from small
  streams (≤ 150 KB of input data). The crafted-block tests cover the large-block paths
  (segmented walks over 64 Ki).
- **Correctness on ARM is qemu's.** qemu-user emulates the instructions faithfully, but
  timing and memory ordering on real hardware were not exercised (the decoder uses
  mutexes and channels only).

## Reproduce

- **The decoder's tests and benchmark:** `cd crates/bunzip && cargo test --release`, then
  `cargo bench`. On aarch64:
  `rustup target add aarch64-unknown-linux-gnu`, `apt install qemu-user
  gcc-aarch64-linux-gnu`, then `cargo test --release --target aarch64-unknown-linux-gnu`
  (`.cargo/config.toml` sets the linker and the qemu runner).
- **Fuzz:** `cargo build --profile fuzz --example fuzz && target/fuzz/examples/fuzz SECONDS SEED
  [FAIL_DIR]` (`--example fuzz`).
- **Real windows:** `curl -r` each 4 MiB window of `latest-all.json.bz2` (at 0, at size
  − 4 MiB, and at size × (2i + 1)/24 for i in 0..11), then `cargo run --release
  --example windows -- OUT_DIR w_*.bin`. It leaves each window's whole blocks as a stream in OUT_DIR,
  for timing.
- **Decode alone:** `cargo run --release --example bzcat -- THREADS < in.bz2 > /dev/null` against `lbzip2 -dc -nTHREADS`
  (`BUNZIP_SIMD=off` for the scalar kernels, `BZ2_INVERSE=plain` for the plain walk).
- **The split both ways:** `.venv/bin/python scripts/test_split_bz2_decoder.py
  dump-slice.json.bz2` (bench/dumpslice.py makes the slice). Then
  `BENCH_DUMP_SLICE=… .venv/bin/python bench/pipeline.py --bz2-native $PWD/src out.json
  SEED` for CI's stage.
- **The real-lines dump:** each window's stream decoded, its first and last (cut) lines
  dropped, the whole entity lines written as `[`, lines with commas, `]`, and compressed
  by `lbzip2 -9`.
