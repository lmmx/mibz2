# What to compute and measure, chapter by chapter

*The Coordinator's interpretation, 25 November 2026. Each item uses data we already have (stage 1's traces, `character/run-20261125T001135Z`) or that stage 2 will produce. Ordered by how directly each one helps a reorganisation decision.*

## 1. The trace as a hybrid arc (Chapter 2)

- **What:** check that each decode's events, as $(t, j)$ pairs from the timestamps and the under-lock sequence numbers, form a hybrid time domain (Definition 2.3), with flows matching the ledger's states.
- **Why:** it makes the model and the measurement the same object. Every later item is computed on these arcs.
- **Cost:** offline, from the bundle. Stage 1's "linear order" identity already checks most of it.

## 2. Event-rate bounds as token buckets (Chapter 2, Example 2.15; Chapter 6, Proposition 6.35)

- **What:** for each event type (issue, start, finish, take), the smallest $N_0$ and largest $1/\tau_D$ such that every window of the trace has at most $(t - s)/\tau_D + N_0$ events. This is the average-dwell-time class, which the book shows is generated by a token bucket.
- **Why:** these are the decoder's true burst and rate limits, per count. The scanner's issue rate bounds everything above the knee, and its burst parameter $N_0$ says how much the window must absorb. That replaces the misapplied Little's-law window sizing of §58 with a measured quantity.
- **Cost:** offline, minutes.

## 3. The completion-time certificate (Chapter 3 §3.3; Chapter 7, Examples 7.6 and 7.35)

- **What:** evaluate $V(x)$ = the maximum of the scanner's, the workers' (over k) and the reader's remaining work along every trace (`decoder-as-hybrid-system.md`). Measure how fast it falls during each phase, and when it fails to fall: the idle gaps, which are the relaxed-condition cases.
- **Why:** if $V$'s fall rate predicts each decode's remaining time well, it is a cheap scorer for any proposed change. Re-run the same evaluation with a lever's predicted effect (a rate changed, a set changed) before building it. That is the bridge from measurement to design.
- **Test:** does $V(x_0)/\text{rate}$ predict the 20 measured walls within the noise, and, the stronger test, stage 2's pulses and held-out rounds without being given their realised durations? Replaying a trace with its own durations only checks the bookkeeping (ChatGPT's distinction). Where it fails, the failure points at the missing state variable (§67: occupancy alone was not enough).

## 4. Sensitivity at the decision surfaces (Chapter 4; Chapter 5 for comparing traces)

- **What:** find the events that sit on thin boundaries:
  - admissions that happen exactly as `issued − taken` reaches W;
  - takes that wait on exactly one head-of-line block;
  - workers that find the queue empty by a hair.
  
  Across the 12–16 rounds at each count, compare traces by graphical closeness, which allows jump times to shift (Theorem 5.25), and find where runs *diverge*.
- **Why:** Chapter 4 shows that tiny timing noise at a thin surface can change the whole run, and the bimodal scanner (fast or slow, run to run) looks like such a split. If divergence starts at a particular surface, that surface is the lever: make the decision robust, for instance with hysteresis (Examples 4.18 and 4.19), or remove it.
- **Cost:** offline from stage 1; stage 2's pulses add controlled perturbations.

## 5. The steady regime (Chapter 8)

- **What:** in each decode's steady phase, find the set the state settles into: occupancy, the share of starved workers, the ready bytes. Check whether it behaves as the invariance principle predicts, as the largest set where the certificate stops falling.
- **Why:** it tells which variables *define* the regime at each count. Stage 1 found that admitted blocks sit at about 20 whatever the window above the knee, a candidate invariant. Single-run versions (Theorem 8.11) need no conserved quantity, which suits measured traces.
- **Caveat:** the decode terminates, so "limits" here mean the long middle stretch, not true $\omega$-limits. Treat the results as descriptions of a steady-state model, and say so.

## 6. Scaling and the knee's geometry (Chapter 9)

- **What:** check homogeneity: if every block's demand is scaled by λ, does the wall scale by λ at every count? Bigger or smaller blocks, or a corpus with a different block-size mix. Then approximate the switching surface near the knee by its tangent cone: the local linear picture of where "workers limit" turns into "the scanner limits".
- **Why:** if the decoder is homogeneous of degree 0 in demand, per-block measurements transfer across corpora by scaling, which is what the adaptive worker cap needs. The cone at the knee says how sharply the regimes switch, the "roundness" that stage 2's 3×3 surface measures.
- **Status:** exploratory; do it after stage 2.
