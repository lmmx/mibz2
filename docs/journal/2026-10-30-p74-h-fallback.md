# P74-H: the shipped kernel's `ptr::copy` as P74's rank ≥ 32 fallback (read-only analysis)

**P74-H** keeps P74's register head and low-rank paths unchanged. Only the rank ≥ 32 tail
shift changes: the masked 32-byte chunks become one overlapping `ptr::copy` of j bytes on
the tail. There is no classifier, counter or handoff.

Nothing was built, run or benchmarked. Gate 1 stays closed.

Labels: **[M]** measured (file cited), **[D]** deduced, **[E]** estimate (assumptions
stated). Scripts are in `hfb/`, and the corpus features are the option C note's
(`features.json`, `fit.json`).

## 0. Verdict: kill H

- **The hurdle** to bring the controls to +3% is a saving per high-rank event of
  **1.27–1.37 ns on random and 1.26–1.66 ns on records on Zen 5** [D from M]. On Zen 4 it
  is 0.72–0.75 ns on random and 0.24–1.86 ns on records, the spread from records' bimodal
  rounds (§4).
- **H's predicted saving** [E]:
  - **At the measured marginal cost of extra fallback instructions:** about 0 on Zen 5,
    and 0.27 ns (random) to 0.55 ns (records) on Zen 4. H's added call, spill and
    mispredicts may make it negative.
  - **Even assuming the fallback is throughput-bound at 4 IPC,** which the data
    contradicts (§3): Zen 5 random 0.76 ns, below its 1.27 ns hurdle.
- **Random fails on Zen 5 under the most favourable model,** so H can't approach the
  hurdle. No experiment is described.
- **The cost to Wikidata:** a call, vzeroupper and head spill per fallback, and more
  mispredict-prone size classes. That is about 5–7% of Wikidata's MTF gain [E].

## 1. Correctness (proof) [D]

**Setup.** The list is L = H‖U: H holds 32 entries in the register, U 224 in memory, and
L[32 + i] = U[i]. A token of rank q ≥ 32 (so j = q − 32, 0 ≤ j ≤ 223) gives the
move-to-front L′ = [L[q], L[0..q), L[q+1..256)].

**Reading it off by position:**
- L′[0] = L[q] = U[j] = v.
- L′[1..=32] = L[0..32) = H, so H′ = [v, H[0..31)], and L′[32] = H[31] = h, so U′[0] = h.
- L′[33..=q] = L[32..q) = U[0..j). In U's indices that is **U′[1..=j] = U[0..j)**: a
  copy of length j, src U, dst U + 1, overlapping upward. That is
  `ptr::copy(U, U.add(1), j)` (memmove semantics).
- L′[q+1..] = L[q+1..], so U′[j+1..224) = U[j+1..224), unchanged.

**The order is required:**
1. read v = U[j] before the copy (for j ≥ 1 the copy overwrites U[j]);
2. read h = H[31] before the head update;
3. write U[0] ← h after the copy (the copy reads U[0] first);
4. H′ is the current head shift (vperm2i128, vpalignr, then v into byte 0), unchanged.

**The endpoints:**
- **j = 0 (q = 32):** v = U[0]; the copy has length 0, a no-op; U[0] ← h; H′ = [v, H[0..31)].
  So L′ = [L[32], L[0..32), L[33..)], which is MTF at rank 32.
- **j = 223 (q = 255, so A = 256):** v = U[223]; the copy writes U[1..=223] from U[0..223),
  223 bytes; its highest write is U[223], the tail's last entry; U[0] ← h. Nothing outside
  U[0..224) is touched.

**The precondition** is q ≤ A − 1 ≤ 255, which the scanner guarantees (§3.2e(k)).

## 3. Memory dependencies between consecutive fallbacks [D from the asm; Agner for the rule]

**The rule** (Agner, as in §3.2e(d)): a load forwards only when it is contained in one
earlier store. A load spanning two stores, or partly covering one, waits for them to
commit (≈ 10–11 c on Skylake and Zen 3; not documented for Zen 4/5).

| | the next token's v byte load | the next fallback's list/tail loads | other |
|---|---|---|---|
| shipped | contained, so it forwards | memmove's [base, +32) spans the 1-byte `*base = v` store and memmove's unaligned stores at base + 1, so it **fails**; so do its later loads | the fast path's documented failure: the 32-byte list load and load at −1 against the 32-byte and 1-byte stores |
| P74 now | contained in an aligned chunk store or the `vpextrb` byte, so it forwards | aligned [p] exactly matches the earlier chunk store and forwards, **except chunk 0** (overlapped by the younger U[0] byte store), which **fails**; unaligned [p − 1] straddles two chunk stores and **fails** (c + 1 failing loads, waiting concurrently) | no list traffic on the fast path |
| P74-H | contained in the youngest overlapping memmove store or the U[0] byte, so it forwards | memmove's [U, +32) spans the U[0] byte and the unaligned stores at U + 1, so it **fails** (as shipped) | V spill/reload across the call: same address and size, forwarded, but about 5–7 c on V's chain; vzeroupper on every fallback |

- **H removes** the per-chunk straddling loads (c + 1 failing loads become those of one
  memmove) and the chunk loop's data-dependent exit branch.
- **H keeps** the commit wait between consecutive fallbacks, the same hazard shipped and
  P74 already share.
- **H adds:**
  - a call per fallback, with V spilled across it. That reverses §3.2e(i–j)'s design
    goal of keeping V live with no ABI save.
  - memmove's size-class branches. The class changes between consecutive fallbacks are
    0.74 (Wikidata), 0.73 (random) and 0.72 (records) per event, against P74's chunk-count
    changes of 0.21, 0.68 and 0.85 [M as rates; mispredict cost E].
  - a zero-length call for j = 0: 8.2% of Wikidata's fallbacks.

## 4. Reconciling with the fit: the excess is fixed per fallback [D from M]

**The per-event excess** of P74 checkpoints over shipped, with the fitted low-rank
saving added back (Δ + g·E_low)/F:

| runner | random | records | lower chunks per F, random / records | P74 − shipped instruction gap, random / records |
|---|--:|--:|---|---|
| Zen 5 | 9.05 c | 9.04 c | 1.26 / 2.97 | +19.9 / +35.0 |
| Zen 4 | 6.72 c | 7.54 c | 1.26 / 2.97 | +19.9 / +35.0 |

- **On Zen 5 the excess is flat:** +15 instructions and 2.4× the chunks per event change
  it by 0.0 c.
- **On Zen 4,** +15 instructions cost +0.8 c, about 0.055 c per instruction (the fit's
  d_c of 0.48 c per chunk).
- **Within P74 itself:** the plain kernel copies lower chunks unmasked (about 3–6
  instructions each), against the checkpoint kernel's 12-instruction masked chunks.
  Checkpoints minus plain per event is:
  - Zen 5: 2.24 c (random), 1.73 c (records);
  - Zen 4: 0.08 c, 0.29 c.

  It is not proportional to chunk count on either runner.
- **So the excess is a fixed per-fallback cost of about 7–9 c,** not instruction
  throughput. Its likely source is the head–tail interplay: the v load forwarded from the
  last fallback's stores, V's cross-lane chain, and the commit wait. That attribution is
  a hypothesis; no counters were read.
- **Removing chunks or instructions therefore recovers little.**
- **The identifiability limits:**
  - two high-rank corpora;
  - one contrast, records against random, which also differ in E_low share (9.5% against
    24%) and runs;
  - plain against checkpoints confounds the chunk code with n kept in memory and with
    layout (1.4–3.1% layout noise);
  - one runner each, and records' bimodal rounds on Zen 4 (medians used).

## 6. The history of the memmove form [M from the record]

- **The P74 branch has two commits,** both measured, both with the masked-chunk tail:
  - cfeb7aa: CI run 41077291982, Zen 4;
  - e57400e: CI run 41081427181, Zen 5.
- **The memmove form was a local build's codegen,** seen in disassembly before the first
  CI measurement and fixed under the protocol's one disassembly fix
  (`2026-10-30-p74-gate1-result.md`: "LLVM had turned the checkpoint kernels' lower tail
  chunks into a `memmove` call").
  - It was memmove for the lower chunks plus a masked top chunk. That is close to H, not
    identical.
  - The fix restored the design the pre-registration had already fixed: call-free
    blended chunks, "so no `memmove` is called on any input", from §3.2e(j)'s goal of
    keeping V live without an ABI save. It was not a choice between measured
    alternatives.
- **No measurement of any memmove-tail P74 exists.** "Memmove beats the chunked tail
  shift" remains an unmeasured hypothesis. This analysis predicts it doesn't, by the
  margin the controls need.
- **The nearest existing evidence** is the plain/checkpoints contrast in §4, which says
  the chunk code's cost is small.

## 7. What would reverse the kill

- A measured per-fallback cost that scales with c or with instructions (a slope well
  above 0.055 c per instruction) on some runner.
- glibc variants (evex/avx512) cheap enough that a below-32 B memmove costs far less than
  modelled, together with a compiler that keeps V live across the call. The ABI forbids
  the latter for ymm registers, so this would mean an inline copy instead of a call.
- An attribution of the 7–9 c fixed excess to the tail's failed forwards specifically,
  which H changes. That needs PMU counters (store-forward blocks, mispredicts) on the
  fallback path. None exist in the record.
