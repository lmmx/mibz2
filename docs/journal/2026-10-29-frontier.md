# The throughput–memory frontier: Seward's trade-off under a shared cache

The user, the research chatbot and the coordinator revisited Seward's 2001 space–time trade-off (`mergedTL` against `indexF`). They asked whether mibz2 can shift it outward rather than move along it: a smaller table, slower for one block, could be faster for the machine if more blocks' tables stay in the L3. The texts are kept verbatim:
- [the user and the researcher](2026-10-29-frontier/seward-frontier-research.md);
- [the coordinator](2026-10-29-frontier/seward-frontier-coordinator.md).

The objective is now a benchmark page, `docs/site/benchmarks/frontier.md`, with its data in `docs/site/assets/data/frontier.json`.

## Where it stands

- **Measured:**
  - the cache-capacity knee (about 14.4 MB of live tables, 0.7 of the i9's L3, at two block sizes; workstation journal §9);
  - the table's compressibility (about 77% of rows in 32-row translation groups; #99).
- **Not shown:**
  - that a compact table navigates as fast;
  - that it can be built directly from the last column;
  - that it gives more throughput from less memory than the best 32-bit configuration, on one machine and workload.

**What series 2 already shows, with its limits stated.** In throughput against live table bytes, y3x3 (1657 MB/s from 10.8 MB of live tables) beats p4 (1206 MB/s from 14.4 MB). p4 is production's best worker count on the i9 in every scaling run. So at the inversion's level, sharing a table among a block's cores already does better than every production configuration measured. That is the second of the page's three stages (Seward's trade-off, cooperative traversal, compact ψ).

It is not a frontier claim:
- it is the inversion, not the decoder;
- it is pinned;
- its memory is computed, not peak RSS;
- it uses 9 cores against 4.
