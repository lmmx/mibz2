# 2026-10-27: mibz2 v2, the plan and where it stands (no timings yet)

mibz2 (`crates/mibz2`, "multi-chain inversion of bzip2"; renamed from the provisional
`bunzip` in d586e4d on #197) is our Rust bzip2 decoder. This entry opens its second round:
a decoder decisively faster than the strongest alternative, pbz2 0.2.0, with which it is
tied today. **Nothing here is measured yet.** It records the plan, the harness built for it,
and what a read of pbz2's source suggests. Branch `mibz2-v2`, on #197's branch.

## Where we start (measured earlier, elsewhere)

- **The bake-off** (bench slice, 79.2 MB bz2 → 1.085 GB, 4 threads, this VM): pbz2/mibz2
  wall 1.00 (CI 0.86–1.16), CPU 0.96; at 1 thread 0.98. Both ≈1.85× lbzip2 `-n4` on wall,
  ≈2.1× on CPU. Peak RSS: pbz2 34 MB, mibz2 99 MB.
- **In the split on CI (#197):** CPU −20.6%, wall −16.6% against lbzip2.
- **mibz2's known weak spots:**
  - a short repeated pattern decodes at 0.67× libbzip2, because the segmented walk loses
    on cache-resident data;
  - incompressible data doesn't scale past one thread, because the sequential scanner
    binds;
  - the scanner binds above ~12 workers.
- **The per-phase costs at 1 thread** (#194's prototype, c/B of output):

  | phase | c/B |
  |---|--:|
  | the walk (12 joined chains) | 14.1 |
  | the T-vector build | 5.8 |
  | MTF | 2.2 |
  | Huffman | 1.9 |
  | RLE1 + CRC | 0.4 |

  The walk unjoined at 16 chains is 4.4 c/B. That leaves a gap of ~10 c/B, which is
  bookkeeping, joining, or the chain count.

## The harness (milestone 1: built, not yet run)

`crates/mibz2/examples/ab.rs`. pbz2 is a dev-dependency for it only (`=0.2.0`, simd
feature), never a dependency of the library.

- **What a run is:** one process decodes one file from disk, end to end, through each
  decoder's own streaming API.
  - mibz2 uses `BzReader::new` or `::parallel`.
  - pbz2 uses `DecoderReader` or `ParallelDecoder::with_threads`.
  - lbzip2 runs as `lbzip2 -dc -nT`, its output read through a pipe.
  - Each run's output is hashed, so all arms' bytes are compared. Each decoder checks its
    own CRCs.
- **What a run records:**
  - wall time and CPU (user + sys);
  - peak RSS (the decoder's own: lbzip2's from `RUSAGE_CHILDREN`);
  - each thread's CPU, sampled from `/proc/<pid>/task` (so a "4-thread" decoder's real
    runnable threads show: e.g. mibz2's 4 workers, its scanner and the reader);
  - the 1-minute load;
  - the cores other processes kept busy during the run;
  - steal.
- **How runs are ordered:**
  - Rounds are interleaved, with the arms' order rotated and reversed round to round.
  - 1-thread runs are pinned to one CPU (`--pin`).
  - Before each run, the harness waits until the others keep ≤ 1.5 cores busy and no
    single CPU more than half busy.
- **Comparing builds:** `ARM@EXE` runs an arm in another build of the harness. The
  baseline is this branch's first build, saved as a binary, so old and new decoders run in
  the same process shape.
- **`ab summary`** gives, per corpus and thread count:
  - best and median wall and CPU;
  - median peak RSS;
  - paired ratios against a reference arm (geometric mean, 95% t-interval over rounds);
  - a same-bytes check.
- **The corpora:**
  - the bench slice;
  - Wikimedia's own blocks: the bake-off's stream of whole blocks from byte-range windows
    of the dump, 66.7 MB → 1.47 GB, reused rather than downloaded again;
  - Silesia;
  - 100 MiB of random bytes;
  - a 64-byte line repeated (200 MiB);
  - the crate's own non-Wikidata corpora (`ab gen`): text, random, one byte, a 7-byte
    pattern, runs, binary records.
- **Status:** it builds, and every arm decodes every corpus to the same bytes in smoke
  tests. The first matrix (5 rounds; mibz2 v1, pbz2, lbzip2; 1 and 4 threads) was started
  and stopped, because another agent's timing job shared the pinned CPU. **No figures are
  reported from it.** The shared lock (`TIMING.lock`) is held around builds and timing
  from now on.

## What pbz2's source suggests (its ideas, to be reimplemented independently)

pbz2 0.2.0 (Soof Golan, MIT). Read for ideas only; nothing has been adopted yet.

- **Its workers decode Huffman too.** A splitter finds candidate block and end markers by a
  SIMD byte-pair scan, and workers decode whole blocks from them. A false marker inside a
  block makes its segment fail as truncated, and the joiner then joins it with the next.
  So there is no sequential Huffman thread: this is the structural fix for our scanner
  bound.
  - Our version would keep our exactness: a block is accepted only if it starts at the
    previous accepted block's end bit, so a false marker can never be taken for a block.
- **Fused Huffman, RLE2 and MTF,** writing bytes straight into the T-vector's words. There
  is no symbols buffer and no last-column copy, which saves a pass and ~1.8 MB a block in
  flight.
- **The MTF's first 16 entries in a 128-bit register.**
- **A 4-lane T-vector build** (`link`): 4 quarters of the column with their own slot
  tables, interleaved, so consecutive equal bytes don't serialise on one counter.
- **2 symbols per bit-buffer refill,** with an 11-bit fast table.
- **The walk:**
  - 16 lanes;
  - 128 evenly spaced starts plus the origin;
  - the segment-start flag in bit 31 of the T-vector entry (no bitmap);
  - segments written to 1 KiB pages of an arena, joined stop-to-start;
  - a whole-walk fallback for short blocks, or where the join does not cover the block
    (periodic blocks);
  - the joined output written back over the T-vector.
- **Output:** RLE1 and the CRC in the worker into a ≤ 2 MB buffer, the rest kept packed and
  expanded by the reader. This and the in-place output explain much of its 34 MB.

## The plan, milestone by milestone

Each milestone is measured with the harness before the next starts.

1. **The M1 matrix:** mibz2 v1 against pbz2 and lbzip2, 1 and 4 threads, every corpus.
   Peak RSS is split into tables, per-worker scratch and queues, at identical threads and
   buffering.
2. **Lane bookkeeping (the walk):**
   - First separate the real bookkeeping cost from the chain count and from joining:
     unjoined at 12 against joined at 16.
   - Then: a stop flag in the entry instead of the bitmap; lane state as raw write
     pointers; cold out-of-line segment ends; more, shorter segments (a cheap end makes the
     idle tail small); a paged arena; and a recheck of random against evenly spaced starts
     (#194 found evenly spaced clustered).
3. **Structural:**
   - the 4-lane build;
   - fused Huffman, RLE2 and MTF into the T-vector, with 2 symbols a refill;
   - a per-block kernel choice (the plain walk for short or periodic, cache-resident
     blocks: the 0.67× case);
   - memory toward ~34 MB;
   - workers that decode Huffman from speculative block markers, joined exactly (the
     scanner bound).
4. **The super-alphabet (LF², KKP 2012):** 5-byte and 8-byte pair entries with a flag for
   an intermediate row that is a segment start, on the multi-chain walk. Building the pair
   table costs about as much as the build itself (a pass with 256 read streams), so only
   measurement can say whether it pays on 3.6 MB blocks.
5. **Precopy:** build it only if the measured repeat lengths in Wikidata blocks predict a
   gain.
