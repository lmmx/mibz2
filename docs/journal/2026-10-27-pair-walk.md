# The pair walk (ψ², two bytes a step): ported from libsais, and slower (#6, #34)

**Result: negative.** A faithful port of libsais 2.12.1's ψ² inverse BWT into mibz2's
flagged segmented walk is byte-identical everywhere and slower everywhere. CI A/B against
0.1.4 (10 paired rounds):

| Corpus | 1 thread wall | 4 threads wall |
|---|---|---|
| wikidata | +40.6% | +24.3% |
| text | +51.5% | +30.4% |
| random | +48.8% | +23.8% |
| records | +21.0% | +23.1% |
| pattern | +25.1% | +21.3% |

Peak RSS is up 1–8%. The branch `perf/pair-walk` is kept as the record.

## Why it was tried

libsais's own cyclic inverse, run on our last columns in the same binary, beat mibz2 on
Wikidata ([the synthesis](2026-10-27-research-synthesis.md), finding 1).
- Its construction advantage was `RUN_LANES`, which shipped in our single-table build as
  #32 (−16% decode).
- After #32, libsais was still 16% faster: 10.86 against 12.92 c/B.
- Its setup/decode split (≈4.2 / ≈6.7 c/B against our ≈2.5 / ≈10.4) put the whole
  remaining gap in the walk.

## What was built

- **The pair table:** row r's entry is `L[r] | ψ²(r) << 8`. The second byte `L[ψ(r)]` is
  F(r), from a 32 KB first-byte table (rows >> 5) and the bucket starts.
- **The build (`build_pairs`):**
  - bigram counts from a byte histogram of each F bucket's slice of L;
  - then a counting sort by bigram (row p in bucket c is bigram (L[p], c));
  - `RUN_LANES`: 16 equal bytes whose LF rows' 16 bytes are also equal go in with one store.
- **The walk (`walk_pairs_flagged`):**
  - a segment start is flagged in its own entry, and its LF row (recorded during the
    build) is flagged too, as libsais does, so a two-row step sees every start;
  - a lane landing on the LF row writes its one byte and ends;
  - a start whose LF row is another start is dropped;
  - a row that is its own LF needs no mark.
- **Multi-cycle ψ:** a valid block whose text is periodic, such as `pattern`, has a ψ with
  several cycles, and fixed points when one byte repeats. Each lane returns to its own
  start or to its LF mark, so it terminates.
- **Tests:** `pair_walk_equals_plain` covers random, periodic and run-heavy columns, at 3
  primary indices and 4 segment counts. The fuzz loop ran 41,743 cases with 0 failures.

## Where the cost went

Wikidata, local, one thread:

| | Build | Walk | Total |
|---|---|---|---|
| mibz2 0.1.4 (ψ) | 2.5 | ≈10.4–10.8 | 13.1 c/B |
| this port (ψ²) | 7.1–7.6 | ≈10 | 17.4–17.6 c/B |
| libsais 2.12.1 | ≈4.2 | ≈6.7 | 10.9 c/B |

- **The build** costs 3× ours. It's the same scatter, but keyed by bigram: 65,536 bucket
  counters and two dependent loads per row, against 256 counters and one.
- **The walk** takes half the steps, but each costs about twice as much. Each pair step
  adds a first-byte lookup (a table load and a compare loop) and a second byte.
- With prefetching, our walk is bound by instructions per step, not by memory latency
  (32 lanes keep enough misses in flight). So halving the dependent loads buys almost
  nothing.
- One trim, a single u16 store and an unchecked build, changed nothing measurable.

## What remains open

libsais walks a ψ² table in ≈6.7 c/B, against our port's ≈10, so its decode loop does
less per step. Its `decode_chains_symbol_rows` (libsais.c L12364 on) runs:
- a shared-offset loop over all chains for `room` steps (the smallest space left in any
  chain's chunk), with no per-chain end check;
- one u16 store per step;
- the mark test as its only branch.

Those mechanics may transfer to our ψ walk without the pair table. The next diagnostic is
the generated code of the two inner loops: instructions, stores and branches per emitted
byte. It's queued after Precopy (#9), together with per-stage figures in the CI bench, so
a walk change shows up as a walk change rather than only in the total.
