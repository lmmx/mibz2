**What was asked:** build the three A2 levers of `docs/journal/2026-11-27-explore/scanner-a2-dissection.md` on top of #1034, in safe Rust, exact.
**What I found:** all three built; no new `unsafe` (the existing BMI2 dispatch only takes `runs` in place of `sel_buf`).
- *Selectors (A2b):* `read_selectors` emits `(group, count)` runs straight into scratch. Every `0` bit repeats the MTF front, so a run of them is one `leading_zeros`. The fast path runs only where `n_sel` bytes of input remain (a selector is at most 6 bits, so no overrun check can fire); otherwise one selector at a time with libbzip2's check after each, coalescing as it goes. The decode iterates runs, so the per-block `sel_buf` rescan is gone, and so is the 18 KiB selector buffer (runs: 72 KiB per scanner scratch, once).
- *Code lengths (A2c):* a 4 KiB const `DELTA_LUT` takes up to 8 delta-coded lengths per 8-bit lookup when 8 lengths remain, the 8 bits are real input (`r.pos <= data.len()`) and every length passed through stays in 1..=20; anything else falls back to the shipped one-length loop, so the error and its bit are libbzip2's.
- *Table build (A2d):* `Huff::fill_lut` writes each root entry once: the first literal of each pairable length builds its K=2 span directly, the rest clone it with a symbol delta, and the long-code pass touches only the tail, assigning `SubLut` pointers in one ascending pass (no `d_arr`). Counts/base/limit/perm are the shipped code unchanged.
- *Exactness:* single-write build bit-identical (every field, stale `SubLut` included) to the kept two-pass `build_into_reference` over 12,000 builds in one reused table (real, incomplete, oversubscribed, alpha 258, 20-bit). Selector and length readers: same result, error and end bit as the old readers on 20,000 cases, fast and near-end paths both. `DELTA_LUT` checked against a bit-by-bit decode for all 256 prefixes. `cargo test --release` (lib 205 incl. libbzip2 parity), debug-mode new tests, `cargo +nightly miri test --lib -- miri_decode_runs_scalar_exact miri_selectors_and_lengths` clean, fuzz-smoke classic/pipeline/service 30 s each with no failures. Scanner digests (every block's symbols and end bit) identical to master on all 7 bench corpora.
- *VM speed (2-vCPU KVM, pinned, 1 thread, `Scanner` over every block, min of 7 passes, interleaved base/new processes):* wikidata **-4.0%** (median 52.0 -> 49.9 ms, new faster in 10/10 pairs); text -2% (5/6); random flat; runs -5%; pattern, onebyte flat; records **+1.0%** (5/6 slower: short selector runs, the dissection's standalone A2b loss there, not fully offset).
- *CI paired bench (run 45957181404, 10 rounds, 37dc112 vs e448bbb, AMD EPYC 4 CPUs):* accepted under PERFORMANCE-POLICY §2. Primary gain wikidata 1T wall -0.3% (-0.7, -0.0); 4T -1.6% (-3.2, +0.1); no primary loss (text 1/2/4T intervals hold 0). Secondary: records 1T +0.3% slower beyond noise; every other point estimate <= +2.9% (pattern 2T, interval -11.8..+20.1), pattern 4T +1.0% (-6.3, +8.8): the #1034 flag's 4T pattern loss does not recur here. Peak RSS at most +5.0% (records 2T). Same bytes everywhere. CI's 2 physical cores mask a scanner cut (workers bind): the scanner lever's value is the i9 k = 8..10 question.
