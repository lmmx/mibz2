## 1. Verified boundary and viable trust root

Run signal blob **b3fce483e5ccf362bad2fadaabbc55c325636814** accepts ready/hold/clear, checks recipe syntax and ready's full SHA/commit existence, then writes tags. It contains no eligibility validator, protected environment or concurrency group. It checks out the workflow's ref, not the requested target for execution. Clear tolerates deletion errors. Its existence does not prove that a caller is entitled to dispatch it. Current tool discovery exposes no GitHub workflow-dispatch method. The incoming comment identifies the connector app, but its shared app/user provenance does not distinguish the Coordinator from other sessions. App permission metadata is not a callable capability or evidence of delegated operator intent. Shell/browser authentication was not probed; prior inability is a reported limitation, not proof that no possible route exists.

**Impossibility with currently verified capabilities:** a legitimate and forged request written by sessions sharing the same login/app, permissions and fields are indistinguishable to a validator restricted to those observations. Hashing or committing either request proves content identity, not authority. A role cursor can support deduplication; it cannot create the missing distinction. Never infer approval from FROM/ACTOR/TO, OWNER association, an arbitrary verified commit signature, or the absence of a visible objection.

Smallest viable *newly authorised* root: an owner-approved, independently enforceable capability restricted to this repository, the fixed validated Run signal endpoint, permitted operations, recipe allowlist, lifetime and operator/delegation epoch. The holder must be isolated from ordinary shared writers; the validator/writer policy and audit state must also be protected from them. Alternatively, an owner-controlled approval of the exact canonical request digest can provide that root. Neither exists as a verified configuration here. A human approval made through the same automation-accessible credential is not separation.

These protect a job, not arbitrary workflow code. With shared lmmx initiating and approving, self-review prevention may block the legitimate owner too; disabling it is not an authentication fix. An isolated initiator/approver arrangement, protection of workflow changes and tag permissions, and plan/support checks are required. ## 2. Minimal contract

Use a versioned, strict canonical JSON document, carried as data only:

- repository numeric ID **1435546475** and full name; fixed purpose/audience Run signal; operation initially **ready** only;
- allowlisted recipe; exact 40-hex target commit; expected existing ready/hold ref state;
- immutable manifest repository/commit/path and SHA-256;
- globally unique request ID, created-at, short expires-at, single-use nonce;
- policy/validator/writer revisions and eligibility epoch;
- authority reference: approved delegation ID, operator identity/session epoch, permitted scope, expiry and verifiable digest-bound approval;
- immutable evidence identities for frozen registration, recipe/driver digest, independent review and relevant safety decisions, required CI inventory and exact tested commit mapping.

No caller-supplied endpoint, workflow path/ref, shell fragment, checkout instruction or arbitrary URL fetching. Reject unknown/duplicate keys, ambiguous encodings and over-size documents. Manifest entries are claims to verify against trusted sources, never a self-signed PASS. Hold/clear are separate operations: unauthenticated narrowing evidence must block a ready decision under A2, but an arbitrary transport sender cannot gain tag-writing rights. Clear must never silently erase a live HOLD; explicit resolution evidence and separate operation permission are required.

A trusted, pinned validator runs from protected code; read-only token by default, no secrets exposed to request parsing and no request-supplied code/actions executed. It independently resolves:
1. authority scope and current operator epoch; exact bytes/hash and unexpired intent; frozen registration and matching recipe;
2. independent review identity/involvement and evidence, not implementer self-certification; live D100/F01 and all applicable restrictions;
3. exact target and ancestry as required by queue policy; declared expected Actions/checks **and** legacy statuses, including trusted producer IDs, contexts, workflow revisions, matrix jobs, attempt IDs and conclusions;
4. all pages of comments, decisions, runs/jobs/checks/statuses needed for completeness. Missing expected checks are UNKNOWN, never success; skipped/cancelled/neutral are not silently green. Preserve failed attempts; choose the applicable latest attempt by the frozen policy, not whichever one passed. PR merge-SHA testing must be mapped explicitly to exact head/base; never substitute the green default branch.
5. any ambiguity, unreadable/deleted evidence, pagination truncation, status-name collision, newer HOLD or unresolved policy conflict fails closed. A snapshot alone is insufficient proof that no subsequent revocation exists.

The writer stays **Run signal**, not a second tag writer. Either an owner-approved validator is added ahead of its privileged job, or a fixed protected bridge hands it a short-lived, digest-bound, single-use decision that the writer revalidates. Dispatch uses a fixed trusted branch/tag ref for workflow code, distinct from the target commit; verify workflow revision has not changed. No arbitrary workflow dispatch. Only the final isolated job receives contents-write. If a bridge uses API dispatch, it additionally needs actions-write; this is a requested permission, not assumed available. GITHUB_TOKEN authenticates that job, not the human mandate. Ordinary request handlers need neither tag nor Actions write.

## 3. Races, replay and recovery

**Two independent state transitions:** request authorisation and eligibility are both revocable. Model NEW → VALIDATED → CLAIMED → SIGNALLED/REJECTED/REVOKED, keyed by repository/request ID and canonical digest. Reuse of ID with different bytes is rejected; edited/deleted source comments invalidate pending intent rather than silently replacing it. Snapshot event body and fetch current body/version; require digest-bound approval so an edit-and-revert cannot reauthorise new content. Redelivery and reruns resume the recorded transition; they never mint fresh authority. Expired delegation or changed Coordinator handoff epoch rejects a previously queued request.

Use a protected append-only evidence record plus compare-and-swap state, not the role cursor as trust root. Reserve the request before mutation, record the exact intended ref tuple, read back the result. Crash after tag creation but before receipt: same request/digest and same target may reconcile as already signalled only with attributable durable evidence; an unexplained same-SHA tag is not proof this request wrote it. Conflicting tag, unknown push outcome or partial clear stops for reconciliation; never force-move/delete to make a retry fit. Final audit includes validation snapshot, policy/authority epochs, request digest, run/attempt and before/after refs. Audit writes are a proposed future permission, not authorised by this review.

Serialize all ready/hold/clear operations for a recipe and revalidate immediately before mutation. GitHub concurrency is not a durable transaction queue: default pending replacement and scheduling order cannot encode revocation priority. No cancel-in-progress around a partially completed ref operation. Durable revocation wins over readiness even if delivered out of order. A CAS on one ref does **not** atomically validate comments, CI, authority and two tags. Those facts must be coordinated through an authoritative eligibility/revocation epoch honoured by every writer. A raw narrowing comment still blocks under A2; do not pretend the derived registry has perfect instantaneous delivery.

**F02 — consumer boundary prevents an end-to-end fail-closed claim today.** In inspected bench/await-submit.sh (blob **30515b4bd180f13905cf935dc79ef198022c981b**), the last check is effectively: if query succeeds AND hold exists, stop. If that query fails, control continues to the atomic marker and just submit. It also does not compare the freshly read ready ref to the earlier chosen SHA. Therefore a successful initial read followed by a failed final read, or a withdrawn/changed ready ref, can still launch the earlier commit. run-queue.sh delegates to this waiter. This is source control-flow evidence, not an executed workstation test.

Even a fixed final query leaves a check-to-execution race: a HOLD can arrive after it. A bridge alone cannot promise immediate revocation across an external workstation. For strict semantics, require a consumer-acknowledged, one-time start lease against the same revocation epoch and define the linearisation point; post-start revocation is a separate cancellation policy. That consumer/protocol change is outside this assignment and needs explicit approval, not a hidden widening. Until the chosen semantics and fail-closed consumer checks are resolved, do not certify the proposed bridge for unattended readiness. This is not a blanket stop on unrelated work; no existing HOLD is lifted.

## 4. Harmless validation plan and owner approval boundary

No bridge implementation or tests of a bridge were run here. The following is a prospective plan, not evidence of working configuration.

**First, offline/recorded fixtures with zero GitHub writes:** positive digest-bound authorised intent with complete green evidence; forged shared-login headers/app identity; unauthorised signing key; edited/deleted or digest-mismatched request; duplicate and conflicting IDs; expiry and handoff revocation; manifest/code substitution; HOLD on a later page; stale policy; missing/red/cancelled Actions or legacy result; old green/new failed attempt; wrong check producer or merge SHA; API error/truncation; concurrent hold before validation, before write and after write; crashes at every state boundary; unexplained existing tags. Assert deterministic acceptance/rejection reasons and no writer calls for every negative case. Treat the consumer's final-query failure and ready-change as explicit rejected cases; simulate start/revoke interleavings. No candidate code checkout/execution.

**Second, only separately authorised read-only end-to-end report:** a dedicated no-write mode/workflow with permissions fixed to read, no dispatch/tag/queue capability, no deployment to a privileged writer and no workstation. Make the fake writer structurally absent, not a boolean next to production credentials. Verify event delivery, exact parsed bytes, complete pagination, authority verification and decision linkage. This proves read-path integration only—not actual writer identity/isolation, tag restrictions, crash atomicity or consumer revocation. ## Sources and limits

Primary GitHub documentation read during this review (10–11 November 2026 UTC); these document platform semantics, not this repository's configuration:

- [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows): issue_comment supports created/edited/deleted and uses default-branch workflow context. Restrict created for intake; later edits are invalidations, not new approval.
- [Triggering workflows](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow): workflow_dispatch/repository_dispatch are exceptions to GITHUB_TOKEN recursion suppression. A token-created comment is not a reliable way to chain jobs; explicit fixed dispatch needs its permission.
- [Workflow dispatch REST](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event): fine-grained Actions write; workflow ref is branch/tag. Current docs show a run-ID response; do not hardcode an older empty-response assumption without pinning/verifying API version.
- [Environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments): reviewer/self-review/bypass controls. Availability and effective settings remain unverified here.
- [Concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency): group serialization and queue limitations, not a cross-resource transaction.
- [Checks](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference) and [legacy statuses](https://docs.github.com/en/rest/commits/statuses#list-commit-statuses-for-a-reference): separate paginated APIs. Check-run listing has a 1000-suite limit; use suite enumeration or reject incomplete evidence. Trusted expected inventory is still required.
