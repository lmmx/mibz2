## 2. Trace the actual build and causal paths

I compared v0.5.6 `530ed404` and #630's `9743bbe0`. The relevant unchanged blobs include `Cargo.lock`, the scanner block code, `cells.rs`, `mtf.rs`, `rle.rs`, `read.rs` and `stream.rs`. Build profile and dependencies match. The `moonshot` feature is off by default and its `Runs::records` change is visibility. The production `parallel.rs` change swaps the generic worker's lazy kernel and extends `is_lazy`. It does not change the source scheduling plan, thread counts, windows or shared queue code. The timed `ab` executables also differ in harness code. The addendum's aggregate text size delta includes those changes. It neither locates the hot region nor describes the installed CLI/Python layout. **Layout can be causal.** A stable layout penalty for the release binaries is a deployed cost, even if a later build shifts it away. This differs from round-to-round noise. A/B timing of two exact binaries estimates their net effect. It cannot decompose dispatch and layout by itself. A same-build forced-fallback control and independent layout variation can help distinguish those mechanisms. Their effects must stay separate from the release pair. Compiler-dependent layout effects on runtime are documented by Curtsinger and Berger. [Stabilizer](https://people.cs.umass.edu/~emery/pubs/stabilizer-asplos13-draft.pdf)

## 3. Cachegrind catches mechanisms, with limited negative evidence

An Ir difference of 0.1% can be a triage signal for a predeclared diagnostic on a specific denominator. It has no general conversion to wall time, and there is no cited A/A baseline or sensitivity calculation binding it to the 2% wall concern. Equal whole-process counts can conceal compensating changes or dilute changes in rejected-block work under startup, entropy decoding and I/O. Equal counts also permit different data dependencies, cache behavior and branches. Short-circuiting makes a fixed per-block estimate especially speculative across corpora and block sizes.

Use matching toolchains, input hashes and relevant feature/CPU dispatch. A plain default single-thread arm bypasses the parallel lazy replacement. An explicit one-worker diagnostic can help localise code, and the real parallel entry point is needed for any claim about that path. Require byte equality and an actual path witness on the pinned production arm. Attribute counts to the worker/phase as well as whole process, and check same-build repeatability for threaded runs. Separate release binaries, a forced-fallback diagnostic and any layout controls. If the probe only supports simulated caches or emulated dispatch, state that scope.

Record I1 and last-level instruction misses, D1 and last-level data misses split by read/write, and branch diagnostics with cache/branch simulation explicitly enabled. Use these as attribution or investigation triggers. I would gate neither Ir nor simulated misses as a substitute for end-to-end non-regression. The simulator has a basic model and lacks native threading, physical mappings, TLB and speculative effects. Cachegrind's Ir count is for the instrumented execution. It is not native PMU evidence. Native cycles/instructions and appropriate front-end, cache and branch counters can help explain a wall effect on the target if the maintainer approves work there. [Valgrind manual, §§5.2.11 and 5.8](https://valgrind.org/docs/manual/cg-manual.html)

## 4. Policy and release decision

The proposed prospective exemption still creates the loophole. A candidate can avoid a timed guard simply by routing zero blocks on that corpus while changing the common worker type or fallback cost. That selects a weaker measurement for the candidate after the guard result. PERFORMANCE-POLICY §2 preserves the registered corpora and guards, and its limited machine-specific inactivity case also requires a neutral paired CI bench. #630 substitutes OpenCells wherever the lazy worker route is selected, including outside the i9 trim. “Zero open admissions in this test input” is insufficient to show structural inactivity on any hardware.

An explicit maintainer risk acceptance for this exact release would be a distinct decision with an accountable scope. It would need to identify the unmet guard, plausible wrapper/layout and mixed-stream risk, and the exact builds and hardware covered. Keep that visible beside NOT ADOPTED. The label “prospective” by itself does not answer why a new test would decide a failed candidate with weaker evidence. Retain rule 2 on primary losses, rule 3 for classed secondary losses, and the normal CI, correctness and release requirements. [Policy](https://github.com/lmmx/mibz2/blob/ef25d39d3a3a3cdb33cc8fb426fd1271dbed6c37/docs/team/PERFORMANCE-POLICY.md#L29)

**Material cost omitted:** the release runbook's §§3.4 and 5c require recalibrating the worker trim when work/block, working set or scratch changes. Open changes those costs. The archived forced-worker comparisons are useful context and do not cover that prescribed pinned/unpinned release sweep. Unless a qualifying result for the actual release is identified or the maintainer explicitly resolves the rule, the claimed “no i9 hours” covers the diagnostic alone. [Release runbook](https://github.com/lmmx/mibz2/blob/ef25d39d3a3a3cdb33cc8fb426fd1271dbed6c37/docs/RELEASING.md#L163)

**Decision-value amendment:**

1. Preserve the pause on #635. Its power requirement concerns detecting a true +2% shift under stated pilot models. It gives neither an equivalence confidence statement nor a universal guarantee at ≥2%, and repeated execution of the same binary pair does not separate layout mechanisms. It can detect a real penalty in the actual pair, which is useful when deciding whether that pair is acceptable.
2. Hold #630 for the maintainer's decision. If the requested next fact is whether the wrapper materially changes the refused/column path, the cheapest increment is a bounded diagnostic combining assembly attribution and deterministic profiles with clear positive and negative controls. A clean diagnostic weakens particular hypotheses. It cannot establish that the release meets the wall-time gate.
3. Choose openly between keeping Open out of 0.5.7, an explicit scoped acceptance of the residual risk, or a short preregistered native decision check with a defined inconclusive outcome and preserved corpora/limits under a prospective ruling. If releasing Open remains the objective, treat any required trim check as part of the cost and coordinate evidence with it. The release also bears possible non-i9 lazy-path and mixed-stream effects. A cheap check limited to zero-route inputs from one i9 cannot cover those.
4. Adopt the memo's decision-value requirement with one addition: specify what a pass, fail and inconclusive result would each change, and count cumulative workstation cost across successive proposals. A cheap result that leaves the release decision exactly where it started is optional engineering information.
