Mission

Prepare and qualify one matched, three-arm complete-decoder benchmark on Louis's i9-10900K workstation, comparing Segmented, original Cells and selective-materialisation Cells.

Our objective is to establish whether the 11.8% Wikidata improvement previously measured on this workstation can be improved further by the selective-materialisation optimisation in PR #380.

Do not merely propose a benchmark. Prepare the complete executable recipe, validate it, obtain the required reviews, and bring it to the workstation's ready queue. The owner will execute the queued run through the existing workstation protocol.

1. Build a valid three-way comparison

Prepare three arms:

A — Segmented

The existing production Segmented decoder, with Cells disabled.

B — Original Cells

The corrected Cells implementation from #365.

C — Selective Cells

The exact successful selective-materialisation implementation from #380.

The critical requirement is that these comparisons use equivalent surrounding decoder code, compiler flags, harness and input data. Construct a common-tree comparison wherever possible, changing only the intended inversion implementation.

Make the source relationship explicit. Do not accidentally compare an older production decoder against a newer entire decoder and attribute the difference to Cells.

Use identical optimised Rust release settings for all three arms. Archive commit identities, binary digests, compiler version, build flags and verified input hashes.

Do not modify the actual Cells implementation or combine this with PR #379.

2. Freeze the experiment before measurement

The primary experiment should use:

- The i9-10900K workstation.
- One pinned physical core, avoiding simultaneous use of its SMT sibling.
- Uninstrumented complete-reader decoding.
- The existing pinned Wikidata dataset.
- Balanced, alternating three-arm runs.
- A predeclared finite number of paired rounds.
- The repository's existing confidence-interval estimator.
- Complete output parity against the reference decoder.

Preserve the existing settling and machine-conditioning requirements. Record CPU topology, affinity, clock-related information and the relevant workstation environment.

Cover all seven existing corpus families to expose regressions.

If a multi-threaded comparison is supported and would answer a distinct production question, include it as a separately identified, prospectively registered part of the programme. Do not assume the one-core Cells results apply to the cooperative/team decoder.

Use the smallest credible measurement programme. No unbounded repetitions, favourable-result selection or rerun-to-pass.

3. State the performance decisions in advance

Report at least these matched ratios:

1. Original Cells / Segmented.
2. Selective Cells / original Cells.
3. Selective Cells / Segmented.

The main questions are:

- Does original Cells reproduce a material Wikidata advantage over Segmented on this i9 under the new matched build?
- Does selective materialisation produce a further improvement on the i9?
- What is the resulting total Wikidata advantage?
- Are the benefits preserved across the relevant corpus families?
- What are the actual memory costs?

Report wall time, CPU time, native peak RSS, confidence intervals and absolute measurements.

Success requires a statistically credible complete-reader improvement, not merely fewer writes or faster isolated induction steps.

A combined improvement approaching 14% over Segmented would be encouraging, but is a hypothesis, not a required target.

Keep the previously observed pattern and onebyte regressions visible. A successful Wikidata result does not automatically justify enabling Cells for every input.
